# RodSki 探索测试 vs 传统测试对比

## 核心差异

| 维度 | 传统测试 (rodski run) | 探索式测试 (ExploreAgent) |
|------|---------------------|------------------------|
| **测试方式** | 固定步骤脚本 | AI 智能探索 |
| **测试路径** | 预定义，100% 可重复 | 动态生成，启发式探索 |
| **发现能力** | 验证已知功能 | 发现预期外问题 |
| **维护成本** | 高（手工编写 XML） | 低（AI 生成命令） |
| **可重复性** | 100% | 60-80%（取决于策略） |
| **执行速度** | 快（确定性） | 慢（需要决策） |
| **适用场景** | 回归测试、验收测试 | 探索测试、集成测试 |
| **证据链** | 完整（XML + 日志） | 完整（Finding + 证据） |

## 详细对比

### 1. 测试编写方式

**传统测试：**
```xml
<!-- 需要手工编写 XML 用例 -->
<case id="tc001" name="登录测试">
    <test_step action="navigate" data="LoginURL"/>
    <test_step action="type" model="LoginPage" data="ValidUser"/>
    <test_step action="verify" model="HomePage" data="WelcomeMsg"/>
</case>
```

**探索式测试：**
```python
# 只需定义探索约章
charter = CharterCard(
    goal="探索登录功能",
    scope={"entry_point": "http://localhost:8000/login"},
    oracle=["登录成功", "错误提示友好"]
)
# AI 自动生成测试命令
```

### 2. 测试执行流程

**传统测试：**
```
XML 用例 → 解析器 → 关键字引擎 → 驱动层 → 结果收集
           (固定)      (确定性)      (可重复)
```

**探索式测试：**
```
Charter → AI 决策 → 命令生成 → 关键字引擎 → 驱动层 → Finding 分类
         (智能)     (动态)       (确定性)      (智能)
```

### 3. 发现能力对比

**传统测试能发现的问题：**
- ✅ 预期功能不工作
- ✅ 已知边界条件错误
- ✅ 固定数据回归
- ❌ 预期外的边界条件
- ❌ 集成后的意外行为
- ❌ 新引入的 UI 问题

**探索式测试能发现的问题：**
- ✅ 预期外的边界条件
- ✅ 集成后的意外行为
- ✅ UI/UX 问题
- ✅ 性能边界问题
- ✅ 浏览器兼容性问题
- ❌ 精确的回归验证（可重复性不足）

### 4. 真实案例对比

#### 案例 1: 登录功能测试

**传统测试：**
```xml
<!-- tc_login_valid.xml -->
<case id="tc_login_001">
    <test_step action="navigate" data="LoginURL"/>
    <test_step action="type" model="LoginPage" data="ValidUser"/>
    <test_step action="verify" model="HomePage" data="WelcomeMsg"/>
</case>

<!-- tc_login_invalid.xml -->
<case id="tc_login_002">
    <test_step action="navigate" data="LoginURL"/>
    <test_step action="type" model="LoginPage" data="InvalidUser"/>
    <test_step action="verify" model="LoginPage" data="ErrorMsg"/>
</case>
```

**发现的问题：**
- ✅ 有效凭证登录成功
- ✅ 无效凭证显示错误

**未发现的问题：**
- ❌ 空用户名时前端验证失败
- ❌ SQL 注入尝试导致后端报错
- ❌ 超长密码导致页面卡顿

**探索式测试：**
```python
charter = CharterCard(
    goal="探索登录功能的稳定性和边界条件",
    scope={"entry_point": "http://localhost:8000/login"},
    oracle=["登录流程稳定", "错误提示友好", "无安全问题"]
)
```

**发现的问题：**
- ✅ 有效凭证登录成功
- ✅ 无效凭证显示错误
- ✅ 空用户名前端验证失败（BUG）
- ✅ SQL 注入尝试被拦截但错误提示不友好（USABILITY）
- ✅ 超长密码导致响应变慢（PERFORMANCE）

#### 案例 2: RodSki 框架集成测试（v9.2.3 真实发现）

**传统测试（CLI）：**
```bash
rodski run case/
# ✅ 所有用例通过
```

**探索式测试（Python API）：**
```python
# 在 Python 环境中通过 ExploreAgent 调用 RodSki
agent = ExploreAgent(execute_command_fn=execute_command)
session = agent.explore_loop()
```

**发现的问题：**
- 🐛 ConfigManager 无法序列化（CLI 不会触发）
- 🐛 Playwright Sync API 在 asyncio 环境冲突（CLI 不会触发）

**价值体现：**
探索式测试通过**不同的集成路径**，发现了传统 CLI 测试无法发现的框架边界问题。

### 5. 维护成本对比

**传统测试维护：**
```
需求变更 → 修改 XML 用例 → 修改 Model → 更新 Data → 验证执行
          (手工)         (手工)      (手工)     (手工)

每个功能点需要：
- 编写 Case XML（5-10 行）
- 定义 Model 元素（3-5 个）
- 准备测试数据（2-5 行）
- 验证数据（2-5 行）

工作量：15-25 行 XML，约 30-60 分钟/用例
```

**探索式测试维护：**
```
需求变更 → 更新 Charter → 重新探索
          (5 行 Python)   (AI 自动)

每个功能点需要：
- 更新 Charter goal（1 句话）
- 调整 scope/oracle（可选）

工作量：1-10 行 Python，约 5-10 分钟/约章
```

**维护成本比：** 探索式测试约为传统测试的 **1/5 - 1/10**

### 6. 执行效率对比

**传统测试：**
- 解析 XML: 10-50ms
- 执行关键字: 100-500ms/步
- 收集结果: 10-20ms
- **总计**: 2-10 秒/用例（10 步）

**探索式测试：**
- AI 决策: 500-2000ms/步（LLM 调用）
- 执行关键字: 100-500ms/步
- 证据采集: 200-500ms/步（失败时）
- **总计**: 20-60 秒/会话（20 步）

**执行速度比：** 探索式测试约为传统测试的 **1/5 - 1/10**

### 7. 适用场景建议

#### 优先使用传统测试的场景

1. **回归测试** - 需要 100% 可重复验证
2. **验收测试** - 明确的验收标准
3. **合规审计** - 需要固定证据链
4. **性能基准** - 精确的性能测量
5. **批量执行** - 大规模并发执行

#### 优先使用探索式测试的场景

1. **探索新功能** - 功能刚开发完成，需要快速验证
2. **集成测试** - 多模块集成后的验证
3. **边界探索** - 发现预期外的边界条件
4. **回归增强** - 传统测试的补充
5. **功能发现** - 在不熟悉的应用中建立理解

#### 最佳实践：组合使用

```
1. 探索式测试（发现问题）
   ↓
2. 将重要 Finding 转化为传统测试用例
   ↓
3. 传统测试（回归保护）
   ↓
4. 定期运行探索式测试（发现新问题）
```

### 8. 证据链对比

**传统测试证据：**
- XML 用例（完整步骤）
- 执行日志（每步结果）
- 截图（失败时）
- HTML 报告（汇总）
- 可追溯性：100%

**探索式测试证据：**
- Charter（探索目标）
- Finding（发现的问题）
- 证据包（截图、错误、DOM）
- HTML 报告（可视化）
- 可追溯性：70-80%（部分动态路径）

### 9. 成本收益分析

| 项目 | 传统测试 | 探索式测试 |
|------|---------|-----------|
| **初始投入** | 高（编写用例） | 低（定义约章） |
| **执行成本** | 低（快速执行） | 中（AI 决策） |
| **维护成本** | 高（手工更新） | 低（自动适应） |
| **发现能力** | 中（已知问题） | 高（预期外问题） |
| **可重复性** | 高（100%） | 中（60-80%） |
| **ROI** | 长期高 | 短期高 |

### 10. 迁移策略

#### 从传统测试迁移到混合模式

**阶段 1: 评估**
- 识别高价值探索场景
- 评估现有用例覆盖率
- 确定探索优先级

**阶段 2: 试点**
- 选择 1-2 个功能模块
- 编写探索约章
- 运行探索会话
- 对比 Finding vs 现有用例

**阶段 3: 扩展**
- 将重要 Finding 转化为传统用例
- 扩展探索约章到更多模块
- 建立定期探索节奏

**阶段 4: 优化**
- 优化 Charter 设计
- 调整探索策略
- 完善 Finding 分类

## 总结

**核心观点：**
1. 探索式测试**不是替代**传统测试，而是**互补增强**
2. 传统测试保证**已知功能正确**
3. 探索式测试挖掘**功能盲区**
4. 最佳实践是**组合使用**两种测试方式

**选择建议：**
- 需要**严格回归**？用传统测试
- 需要**快速探索**？用探索式测试
- 需要**完整覆盖**？两者结合

**投资建议：**
- 核心功能：传统测试（70%） + 探索式测试（30%）
- 新功能：探索式测试（70%） + 传统测试（30%）
- 边界场景：探索式测试（90%） + 传统测试（10%）
