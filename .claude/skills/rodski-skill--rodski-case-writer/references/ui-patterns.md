# RodSki UI 模式

编写或修复普通 RodSki Web UI 流程时使用本文。实时契约仍以 `TEST_CASE_WRITING_GUIDE.md` 为准；本文是从 `$HOME/TestCase/improve` 提炼出的紧凑模式索引。

## 流程形态

- 每个 case 保留一条稳定入口路径。不要在同一个 case 中混合 URL 直达入口和菜单搜索入口。
- 登录和导航放在 `pre_process`，业务动作放在 `test_case`，浏览器清理放在 `post_process`。
- 完整登录使用 `navigate -> type -> 仅必要时短等待 -> verify`。如果 session 已存在，导航到稳定落地页并验证身份，而不是盲目重输凭据。
- 跨角色流程在切换平台或账号前使用 `close -> navigate -> login -> verify`。
- 连续 UI 原子操作属于同一个交互单元时，合并到一条数据行。
- 决策表保留一个 case，并在有用时用带 `group`、`tag`、`depends` 的 `scenario` 块拆分组合。

## 状态与等待

- 优先使用状态驱动的 `verify`，而不是固定 `wait`。
- 固定等待只保留在无法通过就绪文本、状态、稳定定位器或定向 evaluate 轮询表达的真实异步边界。
- 搜索框必须表达触发方式：仅输入搜索、Enter、blur，或显式搜索按钮。
- 保存流程必须验证真实结果：toast、弹窗关闭、XHR 结果、页面跳转、列表行、状态文本，或被阻止的校验状态。
- 对直达路由入口，验证页面标题、业务按钮或权限/引导页状态。只有 URL 不代表就绪。

## 验证

- 将 `_verify` 数据视为期望业务值，而不是描述性注释。
- 如果 verify 是精确匹配，写完整的实际页面值；不要使用模糊关键词。
- 对多个合法结果，建模显式条件或拆分验证路径。不要把多个结果强塞进一个精确期望字符串。
- 如果日志显示 “0 fields verified”，先检查 model/data 绑定；这通常是模型解析为空，不是真正通过。
- 对短暂 toast，优先使用出现即通过条件，或在产生它的动作附近检查页面文本。

## 复杂 UI 桥接

- 只有当内置关键字无法可靠表达 UI 状态时才使用 `evaluate`：富文本编辑器、组件级轮询、授权滑块处理，或受控清理循环。
- `evaluate` 必须返回有用状态或抛出可操作错误。不得返回固定成功。
- 任何白盒 UI 桥接之后，都要回到通过 `verify` 和 model/data 行进行的常规 RodSki 验证。
- 只有在自有测试环境中，且组件状态、token 和校验端点可见且已授权时，才可以处理滑块验证码。

## 调试纪律

- 只使用最新运行证据。不要用旧截图解释新失败。
- 一次只修复一个失败层：case 节奏、model 定位器、data 输入，或 verify 期望。
- 如果页面仍处于中间状态，修复时序/就绪。如果找到了正确节点但文本不同，修复期望数据或定位器提取粒度。
