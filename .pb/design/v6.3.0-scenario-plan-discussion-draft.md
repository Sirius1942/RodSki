**状态**: 讨论稿，未实现

**创建日期**: 2026-05-07  
**更新日期**: 2026-05-07

## 1. 背景问题

当前一些长流程、判定表类用例通过 `<if condition="是 == 是">` 控制某组步骤是否执行：

```xml
<if condition="是 == 是">
  <!-- INV-001 - 仅开票 + 普通发票 + 商品税率13 + 开思券税率6，保存成功 -->
  <test_step action="navigate" data="GlobalValue.DefaultValue.InvoiceConfigURL"/>
  ...
</if>
```

这个写法本质上不是运行时条件判断，而是**测试场景执行开关**。它能方便测试人员临时缩短长流程执行时间，但存在几个问题：

1. `<if>` 语义被滥用，和真正的运行时分支混在一起。
2. 执行开关散落在 case XML 中，需要频繁改用例文件。
3. 无法按测试计划、测试用例、测试场景集中配置执行范围。
4. 单用例、单 scenario、单 step 调试入口不清晰。
5. 执行范围配置缺少可版本管理、可 diff、可被 Agent 直接读写的事实来源。
6. 显式测试计划和按 tag 执行是两种执行范围来源，如果不做边界裁决，会出现“plan 明确关闭但 tag 又命中”的冲突。

v6.3.0 的目标是把“静态执行范围选择”从 case XML 的 `<if>` 中移出来，并明确两种合法入口：显式 plan 执行和 tag/group 临时选择器执行。

## 2. 核心设计决策

### 2.1 测试计划用 XML，不进 SQLite

v6.3.0 不引入 SQLite 测试计划表。

```text
测试计划事实来源：plan/{测试目的}_{测试类型}.xml
测试数据事实来源：data/data.sqlite
全局变量事实来源：data/globalvalue.xml
用例事实来源：case/*.xml
模型事实来源：model/model.xml
```

**明确不做**：

1. 不新增 `rs_testsuite` / `rs_test_plan` / `rs_execution_plan` 等 SQLite 表。
2. 不把测试计划写入 `data/data.sqlite`。
3. 不把 plan XML 作为测试数据加载。
4. 不使用单一 `plan/plan.xml` 聚合全部测试计划。
5. 不在 v6.3.0 第一阶段开发 rodski-vscode 可视化配置页。

### 2.2 为什么不需要测试计划数据库

测试计划是执行配置，不是测试数据。用 `plan/*.xml + CLI` 可以满足第一版需要，并保持 RodSki XML 活文档风格：

1. 每个 plan XML 可读、可改、可 diff，适合 Git review。
2. Agent 可以直接生成、解释、修改测试计划。
3. 没有可视化页面时，SQLite 的价值不明显，反而引入同步复杂度。
4. XML 删除或改名 scenario 后，plan 中遗留引用可以在 `plan validate` 中提示，不需要数据库迁移。
5. `data/data.sqlite` 继续只承载 `type` / `send` / `verify` / `DB` 所需测试数据，职责清晰。

### 2.3 `<if>` 回归运行时分支语义

v6.3.0 后：

| 机制 | 用途 |
|------|------|
| `<scenario>` | 表达 case 内一个可独立选择的测试场景 |
| `plan/{测试目的}_{测试类型}.xml` | 表达本次测试计划要执行哪些 case / scenario / step |
| `--tag` / `--group` | 临时选择器，运行时从 XML 元数据生成一次性执行范围 |
| `<if condition="...">` | 只表达真正的运行时动态条件分支 |

### 2.4 两种执行入口，一个最终模型

v6.3.0 支持两种执行入口，但 RodSki 内部只有一种最终执行模型：

```text
显式 plan XML
  或
tag/group 临时选择器
  ↓
TestPlanSelection（最终执行选择结果）
  ↓
SKIExecutor 确定性执行
```

| 模式 | 命令 | 执行范围来源 | 是否落盘 | 适合场景 |
|------|------|--------------|----------|----------|
| 显式 plan 模式 | `rodski run @invoice_tax_point_smoke` | `plan/invoice_tax_point_smoke.xml` | 是 | CI、发布回归、稳定冒烟、共享调试计划 |
| tag/group 选择器模式 | `rodski run --tag smoke` | `case/*.xml` 中的 scenario 元数据 | 否 | 本地临时验证、快速筛选、Agent 探索执行 |

冲突裁决：

1. `@plan_id` 和 `--tag` / `--group` / `--exclude-tag` / `--priority` 等 selector 是两类执行范围来源，**固定互斥**。
2. `rodski run @invoice_tax_point_smoke --tag smoke` 必须报错，不做隐式合并、交集过滤或优先级裁决。
3. `@plan_id` 只能与环境、日志、录制、dry-run 等非执行范围参数组合；不能与任何执行范围 selector 组合。
4. 如需把 tag/group 结果长期保存，使用 `rodski plan create ... --from-tag/--from-group ...` 生成 plan XML 后再执行。
5. 本设计不提供 plan 后过滤模式；`--filter-tag` 不作为 v6.3.0 及当前后续规划的一部分。

## 3. 目录结构

标准测试项目目录新增 `plan/`：

```text
project/
├── case/
│   └── xxx.xml
├── model/
│   └── model.xml
├── data/
│   ├── data.sqlite
│   └── globalvalue.xml
├── plan/
│   ├── project_full.xml
│   ├── invoice_tax_point_smoke.xml
│   ├── invoice_tax_point_negative.xml
│   └── invoice_tax_point_step_debug.xml
├── fun/
└── result/
```

说明：

1. `plan/` 下每个 XML 文件对应一个测试计划。
2. 文件名采用 `{测试目的}_{测试类型}.xml`，例如 `plan/invoice_tax_point_smoke.xml`。
3. `plan/` 不属于 `data/`，不违反 `data.sqlite` 是唯一测试数据文件的约束。
4. v6.3.0 第一版固定识别 `plan/*.xml`。
5. 文件名 stem 即测试计划 ID，例如 `plan/invoice_tax_point_smoke.xml` 对应 `@invoice_tax_point_smoke`。
6. `rodski run` 未指定计划时优先读取 `plan/project_full.xml`；若不存在但 `plan/*_full.xml` 只有一个，则使用该 full 计划；若存在多个 full 计划则提示用户显式指定 `@plan_id`。

## 4. 核心模型

### 4.1 XML 事实结构

```text
Project
 └── Case（case/*.xml 中的 <case>）
      └── Scenario（<test_case> 内的 <scenario>）
           └── Step（<scenario> 内的 <test_step>）
```

### 4.2 测试计划结构

```text
Project
 └── TestPlan（plan/{测试目的}_{测试类型}.xml 中的 <test_plan>）
      ├── suite：常规测试计划，选择执行哪些 case / scenario
      ├── scenario_debug：单用例按 scenario 调试
      └── step_debug：单用例按 step 调试
```

### 4.3 临时选择器结构

tag/group 选择器不产生持久 XML 文件。它在运行时从 case XML 生成一次性选择结果：

```text
CLI selector（--tag / --group / --exclude-tag）
 └── Temporary TestPlanSelection
      └── Case / Scenario / Step candidates
```

临时选择器不是第二套执行器，也不是第二种结果格式。它只是一种构建 `TestPlanSelection` 的方式。

### 4.4 来源边界

| 信息 | 来源 |
|------|------|
| case id/title/description/component_type/priority/execute | `case/*.xml` |
| scenario id/title/group/tag/depends | `case/*.xml` |
| step action/model/data | `case/*.xml` |
| 默认测试计划 | 优先约定为 `plan/project_full.xml` |
| 每个测试计划执行哪些 case/scenario/step | `plan/{测试目的}_{测试类型}.xml` |
| 临时 tag/group 执行范围 | CLI selector + `case/*.xml` 元数据 |
| 调试 prepare/step_mode/cleanup | `plan/{测试目的}_{测试类型}.xml` |
| 测试数据 | `data/data.sqlite` |
| 全局变量 | `data/globalvalue.xml` |

## 5. Case XML：新增 `<scenario>` 标签

### 5.1 示例

```xml
<case id="invoice_tax_point_decision_table"
      title="开票业务税点-单Case判定表"
      execute="是"
      component_type="界面">
  <pre_process>
    <test_step action="navigate" data="GlobalValue.DefaultValue.ECSellerURL"/>
    <test_step action="type" model="ECSellerLoginPage" data="ec_seller_login"/>
    <test_step action="verify" model="ECSellerWorkbenchCheck" data="seller_login_success"/>
  </pre_process>

  <test_case>
    <scenario id="INV-001"
              group="positive"
              tag="smoke,p0"
              title="仅开票+普通发票+商品税率13+开思券税率6，保存成功">
      <test_step action="navigate" data="GlobalValue.DefaultValue.InvoiceConfigURL"/>
      <test_step action="verify" model="InvoiceConfigCheck" data="page_ready"/>
      <test_step action="type" model="InvoiceConfigPage" data="inv001_yes_normal_13_6_save"/>
      <test_step action="verify" model="InvoiceConfigCheck" data="confirm_modal"/>
      <test_step action="type" model="InvoiceConfigPage" data="confirm_save"/>
      <test_step action="verify" model="InvoiceConfigCheck" data="save_success"/>
    </scenario>

    <scenario id="INV-N01"
              group="negative"
              tag="p1"
              title="仅开票未选开票类型，保存提示请选择零售业务开票类型">
      <test_step action="navigate" data="GlobalValue.DefaultValue.InvoiceConfigURL"/>
      <test_step action="verify" model="InvoiceConfigCheck" data="page_ready"/>
      <test_step action="type" model="InvoiceConfigPage" data="invn01_yes_missing_invoice_type"/>
      <test_step action="verify" model="InvoiceConfigCheck" data="toast_choose_invoice_type"/>
    </scenario>
  </test_case>

  <post_process>
    <test_step action="close" data=""/>
  </post_process>
</case>
```

### 5.2 `<scenario>` 属性

| 属性 | 必填 | 说明 |
|------|------|------|
| `id` | 是 | 场景标识。推荐在同一个 case 内唯一；CLI 短写按 scenario id 执行时要求 Project 内唯一。 |
| `title` | 否 | 场景描述，进入 dry-run、日志和报告。 |
| `group` | 否 | 单值分组，例如 `positive`、`negative`、`boundary`。 |
| `tag` | 否 | 多值标签，逗号分隔，例如 `smoke,p0,slow`。 |
| `depends` | 否 | 依赖的 scenario id，逗号分隔。第一版只支持同一 case 内依赖。 |

### 5.3 `<test_case>` 兼容规则

v6.3.0 支持两种写法：

```xml
<test_case>
  <test_step action="type" model="LoginPage" data="L001"/>
  <test_step action="verify" model="LoginPage" data="V001"/>
</test_case>
```

```xml
<test_case>
  <scenario id="SC-001">
    <test_step action="type" model="LoginPage" data="L001"/>
    <test_step action="verify" model="LoginPage" data="V001"/>
  </scenario>
</test_case>
```

兼容语义：

1. 不含 `<scenario>` 的旧 case，继续按原有 case 级步骤执行。
2. 含 `<scenario>` 的 case，plan 可以按 scenario 粒度选择。
3. `<test_case>` 内允许保留裸 `test_step`，但不推荐。裸步骤按 case 级步骤处理，不受 scenario 选择影响。
4. `<scenario>` 内允许继续使用 `<if>`，但 `<if>` 必须是运行时分支，不再作为静态开关。

## 6. Plan XML：测试计划文件

### 6.1 文件路径与命名

```text
plan/{test_purpose}_{test_type}.xml
```

规则：

1. 一个测试计划一个 XML 文件。
2. 文件名由测试目的和测试类型组成：`{test_purpose}_{test_type}.xml`。
3. `test_purpose` 是稳定的测试目的标识，建议使用英文或拼音小写 snake_case，例如 `invoice_tax_point`、`platform_promotion`、`project`。
4. `test_type` 是计划类型标识，建议使用固定枚举：`full`、`smoke`、`regression`、`negative`、`scenario_debug`、`step_debug`、`failed_rerun`。
5. 文件名 stem 是计划 ID，例如 `plan/invoice_tax_point_smoke.xml` 的计划 ID 是 `invoice_tax_point_smoke`。
6. `<test_plan id="...">` 必须与文件名 stem 一致；不一致时 `rodski plan validate` 报错。
7. `rodski run @invoice_tax_point_smoke` 读取 `plan/invoice_tax_point_smoke.xml`。
8. `rodski run` 不指定计划时优先读取 `plan/project_full.xml`；若不存在但 `plan/*_full.xml` 只有一个，则使用该 full 计划；若存在多个 full 计划则提示用户显式指定 `@plan_id`。

命名示例：

| 文件名 | 计划 ID | 用途 |
|--------|---------|------|
| `plan/project_full.xml` | `project_full` | Project 级全量回归默认计划。 |
| `plan/invoice_tax_point_full.xml` | `invoice_tax_point_full` | 开票税点专项全量计划。 |
| `plan/invoice_tax_point_smoke.xml` | `invoice_tax_point_smoke` | 开票税点冒烟计划。 |
| `plan/invoice_tax_point_negative.xml` | `invoice_tax_point_negative` | 开票税点负向专项计划。 |
| `plan/invoice_tax_point_scenario_debug.xml` | `invoice_tax_point_scenario_debug` | 开票税点单场景调试计划。 |
| `plan/invoice_tax_point_step_debug.xml` | `invoice_tax_point_step_debug` | 开票税点单步骤调试计划。 |

### 6.2 示例文件

#### `plan/project_full.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<test_plan id="project_full"
           title="全量回归"
           kind="suite"
           execute="是"
           default_execute="是">
  <!-- project_full 默认执行所有 XML 中 execute=是 的 case/scenario。
       这里只记录显式排除项。 -->
  <case id="invoice_record_query" execute="否"/>
</test_plan>
```

#### `plan/invoice_tax_point_smoke.xml`

```xml
<?xml version="1.0" encoding="UTF-8"?>
<test_plan id="invoice_tax_point_smoke"
           title="开票税点冒烟测试"
           kind="suite"
           execute="是"
           default_execute="否">

  <case id="invoice_tax_point_decision_table" execute="是">
    <scenario id="INV-001" execute="是"/>
    <scenario id="INV-N01" execute="是"/>
  </case>

  <case id="invoice_record_query" execute="否"/>

```

#### `plan/invoice_tax_point_negative.xml`

```xml

<test_plan id="invoice_tax_point_negative"

           execute="是"
           default_execute="否">
  <case id="invoice_tax_point_decision_table" execute="是">

           kind="scenario_debug"
           execute="是"
           default_execute="否">
  <debug prepare="auto" cleanup="否"/>

           execute="是"
           default_execute="否">
  <debug prepare="auto" step_mode="only" cleanup="否"/>
  <case id="invoice_tax_point_decision_table" execute="是">

      <step no="3" execute="是"/>
    </scenario>
  </case>
</test_plan>
```

### 6.3 根节点 `<test_plan>`

| 属性 | 必填 | 默认值 | 说明 |
|------|------|--------|------|
| `id` | 是 | - | 测试计划 ID，必须与文件名 stem 一致。 |
| `title` | 否 | 空 | 显示名称。 |
| `kind` | 是 | - | `suite` / `scenario_debug` / `step_debug`。 |
| `execute` | 否 | `是` | 计划是否启用。 |
| `default_execute` | 否 | `否` | 未显式配置的 case/scenario 是否默认执行。 |

`default_execute` 推荐策略：

| 计划 | 推荐值 | 含义 |
|------|--------|------|
| `full` | `是` | 默认执行所有 XML 中开启的 case/scenario。 |
| `smoke` | `否` | 只执行 plan 中显式选择的内容。 |
| `negative` | `否` | 只执行专项显式选择的内容。 |
| `scenario_debug` | `否` | 只调试显式选择的 scenario。 |
| `step_debug` | `否` | 只调试显式选择的 step。 |

### 6.4 `<case>` / `<scenario>` / `<step>`

```xml
<case id="invoice_tax_point_decision_table" execute="是">
  <scenario id="INV-001" execute="是">
    <step no="3" execute="是"/>
  </scenario>
</case>
```

| 标签 | 属性 | 必填 | 说明 |
|------|------|------|------|
| `case` | `id` | 是 | 引用 case XML 中的 `<case id="...">`。 |
| `case` | `execute` | 否 | `是` / `否`，默认 `是`。 |
| `scenario` | `id` | 是 | 引用 case 内的 `<scenario id="...">`。 |
| `scenario` | `execute` | 否 | `是` / `否`，默认 `是`。 |
| `step` | `no` | 是 | scenario 内直接 `test_step` 的 1-based 编号。 |
| `step` | `execute` | 否 | `是` / `否`，默认 `是`。 |

### 6.5 `<debug>` 属性

```xml
<debug prepare="auto" step_mode="only" cleanup="否"/>
```

| 属性 | 默认值 | 说明 |
|------|--------|------|
| `prepare` | `auto` | `auto` / `case` / `none`。 |
| `step_mode` | `all` | `all` / `from` / `only`。仅 `kind="step_debug"` 时生效。 |
| `cleanup` | `否` | 调试完成后是否执行 `post_process`。 |

`prepare` 语义：

| 值 | 行为 |
|----|------|
| `auto` | 执行 `pre_process` + 当前 scenario 中目标 step 之前的步骤。 |
| `case` | 只执行 `pre_process`。 |
| `none` | 不执行任何前置，直接执行目标步骤。 |

`step_mode` 语义：

| 值 | 行为 |
|----|------|
| `all` | 执行整个 scenario。 |
| `from` | 从指定 step 开始，后续步骤继续执行。 |
| `only` | 只执行指定 step。 |

## 7. 执行入口模式与选择规则

### 7.1 统一最终选择结果

无论入口来自显式 plan，还是来自 `--tag` / `--group`，RodSki 执行前都先编译成统一的 `TestPlanSelection`：

```text
XML case/scenario/step 树
  + 显式 plan XML 或临时 selector
  + XML 硬关闭规则
  + depends 依赖规则
  ↓
TestPlanSelection
  ↓
SKIExecutor 执行
```

`TestPlanSelection` 是内存结构，不是新的文件格式。它的职责是给执行器一个确定的 case/scenario/step 列表，以及明确的 skipped 原因。

### 7.2 模式一：显式 plan 执行

执行 `rodski run @invoice_tax_point_smoke`：

```text
1. 读取 plan/invoice_tax_point_smoke.xml。
2. 校验文件内 <test_plan id="invoice_tax_point_smoke"> 与文件名一致。
3. 如果 test_plan.execute="否"，整个计划跳过。
4. 解析 case/*.xml，得到真实 case/scenario/step 树。
5. <case execute="否"> 是硬关闭，优先级最高。
6. 如果 plan 中 case execute="否"，跳过整个 case。
7. 如果 plan 中 case execute="是"，继续判断 scenario。
8. 如果 plan 中 scenario execute="否"，跳过该 scenario。
9. 如果 plan 中 scenario execute="是"，执行该 scenario。
10. 未显式配置的 case/scenario 使用 test_plan.default_execute。
11. 产出 TestPlanSelection。
12. 按 XML 顺序执行。
```

显式 plan 适合 CI、发布回归、稳定冒烟、共享调试计划。它是长期、可复现、可 review 的执行契约。

### 7.3 模式二：tag/group 临时选择器执行

执行：

```bash
rodski run --tag smoke
rodski run --tags smoke
rodski run --tag smoke,p0
rodski run --group negative
rodski run --tag smoke --exclude-tag slow
rodski run --tag smoke --exclude-tags slow
```

语义：

```text
1. 不读取 plan/*.xml。
2. 解析 case/*.xml，得到真实 case/scenario/step 树。
3. 根据 tag/group 条件筛选 scenario。
4. 生成内存中的临时 TestPlanSelection。
5. 不写入 plan XML，不修改 case/model/data/globalvalue。
6. 按 XML 顺序执行命中的 case/scenario。
```

tag/group 选择器适合本地临时验证、快速筛选和 Agent 探索执行。它不是持久测试计划。

tag 组合可以很多，不要求每一种组合都创建 plan XML。只有 CI、发布回归、团队共享、需要 review 或需要复现的执行范围，才建议落成 `plan/{测试目的}_{测试类型}.xml`。

### 7.4 tag/group 匹配规则

| 选择器 | 匹配对象 | 说明 |
|--------|----------|------|
| `--tag smoke` / `--tags smoke` | scenario `tag` + 继承的 `<cases tags>` | 任一 tag 命中即选中；`--tags` 保持兼容，`--tag` 是推荐别名。 |
| `--tag smoke,p0` | scenario tag 集合 | OR 匹配，命中 `smoke` 或 `p0` 即选中。 |
| `--group negative` | scenario `group` | group 是单值，精确匹配。 |
| `--exclude-tag slow` / `--exclude-tags slow` | 已选中的 scenario tag 集合 | 从候选集中排除命中 tag 的 scenario；`--exclude-tags` 保持兼容。 |
| `--priority P0` | case `priority` | case 级过滤；命中后再判断 scenario selector。 |

继承规则：

1. `<cases tags="smoke,login">` 是文件级 tag，文件内 case/scenario 默认继承。
2. `<scenario tag="p0,api">` 是 scenario 级 tag。
3. 有效 tag 集合 = 文件级 tag + scenario 级 tag。
4. v6.3.0 第一版不新增 case 级 `tag` 属性；如后续增加，继承顺序为 file → case → scenario。

### 7.5 显式 plan 与 tag/group 的冲突处理

禁止同时使用显式 plan 与任何执行范围 selector：

```bash
rodski run @invoice_tax_point_smoke --tag smoke
rodski run @invoice_tax_point_smoke --tags smoke
rodski run @invoice_tax_point_smoke --group negative
rodski run @invoice_tax_point_smoke --exclude-tag slow
rodski run @invoice_tax_point_smoke --priority P0
```

以上命令必须报错。错误提示建议：

```text
@plan_id 与 --tag/--group/--exclude-tag/--priority 是两类执行范围来源，不能同时使用。
请使用以下方式之一：
1. rodski run @invoice_tax_point_smoke
2. rodski run --tag smoke
3. rodski plan create invoice_tax_point_smoke --from-tag smoke 后再 rodski run @invoice_tax_point_smoke
```

设计原因：

```text
plan 明确关闭某个 scenario
tag 又命中同一个 scenario
```

如果允许同时使用，就必须回答“谁优先”或“是否取交集”。本设计不提供这种模式：显式 plan 和 selector 必须作为两个独立执行入口，不能在同一次 `rodski run` 中组合。

### 7.6 从 tag/group 生成持久 plan

如果某个 tag/group 选择结果需要长期复用，应生成 plan XML：

```bash
rodski plan create invoice_tax_point_smoke \
  --kind suite \
  --from-tag smoke \
  --title 开票税点冒烟测试

rodski plan create invoice_tax_point_negative \
  --kind suite \
  --from-group negative \
  --title 开票税点负向校验专项
```

生成后的计划进入显式 plan 模式：

```bash
rodski run @invoice_tax_point_smoke
```

### 7.7 调试计划

场景调试：

```bash
rodski run @invoice_tax_point_scenario_debug --debug
```

```text
1. 读取目标 debug plan。
2. 要求 plan 中至少包含 1 个 case/scenario 选择。
3. 默认执行被选中的完整 scenario。
4. prepare 决定是否执行 pre_process。
5. cleanup 决定是否执行 post_process。
6. 不修改 case XML、model XML、data.sqlite 或 globalvalue.xml。
```

步骤调试：

```bash
rodski run @invoice_tax_point_step_debug --debug
```

```text
1. 读取目标 debug plan。
2. 找到 case/scenario/step。
3. 根据 prepare 准备上下文。
4. 根据 step_mode 执行步骤：
   - all：忽略 step 选择，执行整个 scenario
   - from：从 step no 开始执行到 scenario 结束
   - only：只执行 step no
5. cleanup="是" 时执行 post_process，否则保留现场。
```

### 7.8 优先级

显式 plan 模式：

```text
<case execute="否">
  > test_plan.execute="否"
  > plan case execute="否"
  > plan scenario execute="否"
  > plan step execute="否"
  > test_plan.default_execute
```

tag/group 选择器模式：

```text
<case execute="否">
  > selector include 条件
  > selector exclude 条件
  > depends 依赖判断
```

只要上层为 `否`，下层即使为 `是` 或 tag 命中也不会执行。

### 7.9 引用不存在的处理

如果 plan XML 中引用了 XML 中不存在的 case/scenario/step：

| 场景 | 行为 |
|------|------|
| `rodski plan validate` | 报错或警告，列出 stale 引用。 |
| `rodski run @plan_id --dry-run` | 输出 stale 引用提示，不实际执行该项。 |
| `rodski run @plan_id` | 忽略不存在项，并在日志中提示。 |

## 12. Schema 影响

### 12.1 case.xsd

需要在 `case.xsd` 中允许 `<scenario>` 作为 `<test_case>` 的子元素。

第一版建议：

```text
<test_case>
  choice:
    - test_step
    - if / elif / else
    - loop
    - scenario
</test_case>

<scenario>
  choice:
    - test_step
    - if / elif / else
    - loop
</scenario>
```

`scenario` 属性：

```text
id      required string
title   optional string
group   optional string
tag     optional string
depends optional string
```

### 12.2 plan.xsd

新增 `rodski/schemas/plan.xsd`，约束：

1. 根节点为 `<test_plan>`。
2. `<test_plan id>` 必填；是否与文件名 stem 一致由 `rodski plan validate` 校验。
3. `kind` 枚举为 `suite` / `scenario_debug` / `step_debug`。
4. `execute` 和 `default_execute` 枚举为 `是` / `否`。
5. `debug.prepare` 枚举为 `auto` / `case` / `none`。
6. `debug.step_mode` 枚举为 `all` / `from` / `only`。
7. `step.no` 为正整数。

跨文件引用校验不放进 XSD，由 `rodski plan validate` 完成。

## 14. 已确认设计决策

1. **测试计划是一等概念**：测试计划定义执行哪些 case/scenario/step。
2. **v6.3.0 不引入测试计划数据库**：不新增 SQLite 计划表。
3. **`plan/{测试目的}_{测试类型}.xml` 是测试计划唯一事实来源**。
4. **一个测试计划一个 XML 文件**：不使用单一聚合计划文件。
5. **`data/data.sqlite` 继续只承载测试数据**，不承载测试计划。
6. **case/scenario/step 信息以 case XML 为准**，plan XML 不复制 title/group/tag/step 内容。
7. **静态执行开关从 `<if>` 移到 plan XML**。
8. **`<if>` 只保留运行时动态分支语义**。
9. **常规测试计划用 `kind="suite"`**。
10. **单用例按场景调试用 `kind="scenario_debug"`**。
11. **单用例按步骤调试用 `kind="step_debug"`**。
12. **默认计划优先约定为 `plan/project_full.xml`**；若不存在但 `plan/*_full.xml` 只有一个，则使用该 full 计划；否则 CLI 提示显式指定计划。
13. **支持 tag/group 临时选择器执行**：`rodski run --tag smoke` 不读取 plan XML，不落盘。
14. **显式 plan 与 tag/group/priority selector 固定互斥**：`@plan_id` 不能和 `--tag` / `--group` / `--exclude-tag` / `--priority` 等执行范围 selector 同时使用。
15. **显式 plan 和 tag/group 最终都编译为 `TestPlanSelection`**，执行器只消费确定后的选择结果。
16. **v6.3.0 第一版不开发 rodski-vscode 页面**；后续页面应读写 plan XML，而不是单独维护另一套状态。
17. **v6.3.0 不支持跨 Project 执行**；每个 Project 独立维护自己的 `plan/*.xml`。
