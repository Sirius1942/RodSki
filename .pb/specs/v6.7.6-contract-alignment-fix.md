| # | 决策项 | 结论 | 理由 |

## 1. 背景

本轮检查目标是把 RodSki 源代码、XSD、打包配置和 `rodski-demo` 与核心设计约束重新对齐。当前主要问题不是单个 bug，而是四类漂移叠加：

1. XSD 与运行时关键字不一致，导致合法用例过不了 schema，或非法用例被放行。
2. SQLite 数据契约未严格执行，数据缺字段和空验证会被静默跳过。
3. `verify` 对接口/DB 的实际值读取与 `_verify` 期望值解析互相抵消，出现自己跟自己比较。
4. 打包配置存在双 pyproject 和包结构分歧，安装态能力与源码态能力不一致。

v6.7.6 的目标不是扩大语法，而是让实现服从现有契约：三元模型、`data.sqlite` 唯一测试数据、完整 `<location>` 定位器格式、`launch/navigate` 场景化启动、接口/DB 使用 `send/DB + verify`。

## 2. 问题清单与修复方案

### P0-1 `launch` 契约无法通过 case.xsd，运行时也有未定义变量

**现象**

- 文档要求 Desktop 使用 `launch`。
- `case.xsd` 的 `ActionType` 没有 `launch`，包含 `launch` 的用例会被 XSD 拒绝。
- `_kw_launch` 中直接引用未定义的 `model_type`，执行时会报错。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:39`, `TEST_CASE_WRITING_GUIDE.md:1655`
- Schema: `rodski/schemas/case.xsd:170`
- 代码: `rodski/core/keyword_engine.py:1112`, `rodski/core/keyword_engine.py:1122`

**修复**

1. 在 `case.xsd` `ActionType` 中加入 `launch`。
2. 在 `_kw_launch` 内显式计算 `model_type`；当 `model=""` 时按 Desktop target 参数走 `_execute_desktop_launch`，不要落到 Web `navigate` 语义。
3. 增加 `CaseParser` schema 测试：`action="launch"` 应合法。
4. 增加最小运行时单测，覆盖 `model="" data="notepad.exe/TextEdit.app"` 不再触发 `NameError`。

---

### P0-2 `model.xsd` 仍允许旧定位器格式

**现象**

- 契约规定唯一定位器格式为 `<location type="...">value</location>`。
- `model.xsd` 仍允许 `element@value`、`element@locator`、`element@type="id/css/field/..."` 等旧简化格式。
- `ModelParser` 实际只解析 `<location>` 子节点；旧格式会通过 XSD 但被解析器静默丢弃。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:171`, `TEST_CASE_WRITING_GUIDE.md:99`
- Schema: `rodski/schemas/model.xsd:78`
- 代码: `rodski/core/model_parser.py:135`

**修复**

1. `model.xsd` 删除 `ElementType` 中的 `value`、`locator` 属性。
2. `element@type` 只保留为历史 driver/type 兼容入口时必须明确约束；定位器类型不得出现在 `element@type`。
3. `location` 子节点改为 `minOccurs="1"`，接口/DB 中需要静态字段时也用 `<location type="field/static">...</location>`。
4. `ModelParser` 在遇到 `value/locator` 或无 `location` 的元素时抛出清晰错误，避免静默跳过。
5. 增加 XSD 拒绝旧格式的测试。

---

### P0-3 SQLite 行字段一致性没有严格执行

**现象**

- 契约要求同一逻辑表必须显式声明 schema，且所有数据行字段集合完全一致。
- 当前校验只拦截 schema 外多余字段，允许缺字段。
- `type`/`verify` 又会跳过缺字段，导致输入或断言缺失不报错。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:119`
- 代码: `rodski/core/data_schema_validator.py:19`, `rodski/core/keyword_engine.py:778`, `rodski/core/keyword_engine.py:1443`

**修复**

1. `DataSchemaValidator.check_sqlite_schema()` 同时校验 `missing` 和 `extra`，任何行字段集合与 schema 不一致都报错。
2. `type` 和 `verify` 在数据行缺少模型元素字段时失败，而不是 `continue`。
3. 对确实不需要执行的字段，老用例必须显式填 `BLANK`、`NULL` 或 `NONE`。
4. 增加 SQLite 严格校验单测，覆盖缺字段、多字段、完全一致三类。

---

### P0-4 接口/DB `_verify` 使用 `${Return[-1]}` 只报警不失败

**现象**

接口/DB 的 `verify` 本来就从 `Return[-1]` 读取实际值。如果 `_verify` 表的期望值也写 `${Return[-1]}`，执行流程会先把期望解析成实际值，再与实际值比较，断言永远通过。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:292`
- 代码: `rodski/core/keyword_engine.py:1451`

**修复**

1. 非 UI 模型的 `_verify` 数据中出现 `${Return[-1]` 时直接失败。
2. 错误消息说明：接口/DB verify 的实际值已自动来自 `Return[-1]`，期望值必须是字面值或稳定全局值。
3. 增加回归测试，确保 warning 不再放行。

---

### P0-5 DB `verify` 当前可能空校验通过

**现象**

- `ModelParser` 对 database 模型只保存 `__queries__`，没有可供 `_batch_verify` 遍历的字段元素。
- `_batch_verify` 跳过所有 `__*` 键，最后可以在 `results` 为空时仍返回通过。

**位置**

- 代码: `rodski/core/model_parser.py:87`, `rodski/core/keyword_engine.py:1443`, `rodski/core/keyword_engine.py:1540`

**修复**

1. database 模型的 verify 不依赖元素遍历，改为按 `_verify` 数据行字段逐个从 `Return[-1]` 取实际值。
2. 任何 `verify` 若最终比较字段数为 0，直接失败。
3. DB 查询返回列表时支持字段路径：`field`、`0.field`、`[0].field` 三种兼容读取；文档最终推荐一种。
4. 增加 DB verify 单测：正常匹配、字段缺失、不匹配、0 字段四类。

### P1-1 Case XML 的 `data` 属性会解析内置函数

**现象**

契约规定 `${random(...)}`、`${date(...)}` 等内置函数只在数据表字段值中生效，不写在 Case XML 的 `data` 属性中。当前执行器会对每个 step 的 `data` 都调用 `DataResolver.resolve()`，因此 Case XML 中的内置函数也会生效。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:381`, `TEST_CASE_WRITING_GUIDE.md:985`
- 代码: `rodski/core/ski_executor.py:1312`, `rodski/data/data_resolver.py:35`

**修复**

1. Case step `data` 只解析 `GlobalValue.*`、已命名变量和 `Return` 引用；不解析内置函数。
2. 或在解析前检测 `${random(` / `${date(` 等函数调用并给出明确错误。
3. 数据表字段值仍保留内置函数解析能力。

---

### P1-2 `run` 的路径约定与文档冲突

**现象**

文档示例使用 `data="fun/utils/data_process.py"`。当前 `model=""` 时实现会把 `data` 拼到 `fun_dir` 后面，导致 `fun/...` 被解析成 `fun/fun/...`。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:68`
- 代码: `rodski/core/keyword_engine.py:1764`

**修复**

1. `run` 对 `data` 中的可选 `fun/` 前缀做归一化，`fun/desktop/key_combo.py` 与 `desktop/key_combo.py` 都解析到同一个脚本。
2. 保留 `model="工程名" data="script.py args"` 写法。
3. 增加路径解析单测，覆盖 `model=""`、`model="desktop_ops"`、带参数、带 `fun/` 前缀。

### P1-3 `run` 存在内置操作分支，偏离“子进程脚本调用”

**现象**

契约定义 `run` 是在独立子进程中执行 `fun/` 下 Python 脚本。当前 `model=""` 且 `data` 命中内置调用时会走 `_try_builtin_call()`，例如 network mock 相关操作。

**位置**

- 契约: `CORE_DESIGN_CONSTRAINTS.md:53`
- 代码: `rodski/core/keyword_engine.py:1731`, `rodski/builtin_ops/__init__.py:72`

**修复选项**

推荐方案：保留能力但显式产品化为 `run` 的 in-process builtins，并写入核心契约和用例指南；否则需要把这些能力迁移成 `fun/network_ops/*.py` 脚本。v6.7.6 先做决策并加测试，不允许继续处于隐式状态。

**位置**

**修复**

1. `RodskiXmlValidator` 增加 `plan` kind 与 `plan.xsd` 映射。
2. `PlanParser` 统一调用公共 validator。

### P1-5 `rodski init` 与标准模块结构不一致

**现象**

标准模块包含 `plan/`，且 v6.0 起 `data.sqlite` 是唯一测试数据文件。当前 init skeleton 缺少 `plan/`，还提供 `--no-sqlite`。

**位置**

- 契约: `TEST_CASE_WRITING_GUIDE.md:80`, `CORE_DESIGN_CONSTRAINTS.md:77`
- 代码: `rodski/rodski_cli/init.py:19`, `rodski/rodski_cli/init.py:35`

**修复**

2. 默认创建 `data/data.sqlite` 和 `data/globalvalue.xml`。
3. 废弃 `--no-sqlite`；如需保留 CLI 兼容，只允许生成空 SQLite 或打印废弃警告。

### P1-6 打包配置存在双 pyproject 和安装态漂移

**现象**

- 根 `pyproject.toml` 版本是 `6.3.9`，包布局是 `rodski.*`。
- `rodski/pyproject.toml` 版本是 `6.7.3`，包布局是顶层 `core*`、`schemas*`、`rodski_cli*`。
- 曾出现 `rodski_cli` 引用 `from rodski import __version__` 而安装包没有 `rodski` 顶层模块的问题。当前源码中 `rodski/rodski_cli/__init__.py` 已改用 `importlib.metadata.version("rodski")`，但双打包配置仍会让这个问题复发。
- 曾出现 wheel/sdist 安装后缺少 `schemas/*.xsd` 的问题。当前 `rodski/pyproject.toml` 有 `schemas = ["*.xsd"]`，根 `MANIFEST.in` 有 `recursive-include rodski/schemas *.xsd`，但两套布局需要统一验证。
- `rodski/pyproject.toml` 缺少运行时 dependencies，干净安装后可能缺 `xmlschema` 等依赖。

**位置**

- 根配置: `pyproject.toml:5`, `pyproject.toml:33`, `pyproject.toml:70`
- 子目录配置: `rodski/pyproject.toml:5`, `rodski/pyproject.toml:36`
- CLI: `rodski/rodski_cli/__init__.py`

**修复**

1. 明确唯一发布入口。推荐使用根 `pyproject.toml`，包布局统一为 `rodski.*`。
2. 删除或停止使用 `rodski/pyproject.toml`；如短期不能删除，CI 必须同时验证两种构建都可安装。
3. 版本号单源化，`rodski/__init__.py`、根 `pyproject.toml`、发布 tag 不得分裂。
4. package-data 覆盖 `rodski/schemas/*.xsd`，sdist/wheel 安装后用 `importlib.resources` 或解析器真实加载 `model.xsd` 验证。
5. dependencies 以根配置为准，至少包含 `xmlschema`、`pyyaml`、`tqdm`、`psutil`、`requests`；可选能力放 extras。

## 3. 老用例迁移规则

### 3.1 旧 model 定位器格式

旧格式：

```xml
<element name="username" type="id" value="loginUsername"/>
<element name="submit" locator="vision:登录"/>
```

迁移为：

```xml
<element name="username">
  <location type="id">loginUsername</location>
</element>

<element name="submit">
  <location type="vision">登录</location>
</element>
```

如果旧 `type` 表示元素语义类型，而不是定位器类型，迁移到子节点：

```xml
<element name="submit">
  <type>button</type>
  <location type="id">submitBtn</location>
</element>
```

### 3.2 XML 数据文件

旧文件：

```text
data/data.xml
data/data_verify.xml
data/{Model}.xml
data/{Model}_verify.xml
```

迁移为：

```text
data/data.sqlite
data/globalvalue.xml
```

执行建议：

```bash
rodski data import <module> --overwrite
rodski data validate <module> --strict
```

迁移后删除 XML 数据文件；`globalvalue.xml` 继续保留。

### 3.3 SQLite 缺字段

v6.7.6 严格模式下，同一逻辑表的每一行都必须包含 schema 声明的全部字段。老用例缺字段时不要依赖“缺字段代表跳过”，应显式写：

- `BLANK`: UI 输入跳过或期望空串，按关键字语义处理。
- `NULL` / `NONE`: 明确表示无值。
- 真实期望值: verify 表优先使用稳定字面值。

### 3.4 接口/DB `_verify` 中的 `${Return[-1]}`

旧写法：

```sql
RegisterAPI_verify.V001.status = ${Return[-1].status}
```

迁移为：

```sql
RegisterAPI_verify.V001.status = 200
```

原因：接口/DB verify 的实际值已经自动从 `Return[-1]` 读取，`_verify` 表只写期望值。

### 3.5 Case XML 中的内置函数

旧写法：

```xml
<test_step action="send" model="RegisterAPI" data="${random(int, 4)}"/>
```

迁移为：

```xml
<test_step action="send" model="RegisterAPI" data="R001"/>
```

并把动态值写到 SQLite 字段：

```sql
username = user_${random(int, 4)}
```

### 3.6 `run` 脚本路径

v6.7.6 建议实现兼容 `fun/` 前缀，所以老用例可保留：

```xml
<test_step action="run" model="" data="fun/desktop/key_combo.py Ctrl+A"/>
```

内部归一化后与以下写法等价：

```xml
<test_step action="run" model="" data="desktop/key_combo.py Ctrl+A"/>
```

### 3.7 Desktop 启动

老用例如果使用 `run launch_app.py ...` 启动桌面程序，后续可迁移为：

```xml
<test_step action="launch" model="" data="TextEdit.app"/>
```

前提是 v6.7.6 修复 `case.xsd` 和 `_kw_launch`。

### 3.8 交付老用例失败排查与修改指南

v6.7.6 发布时必须新增一份面向用户和 AI Agent 的迁移排查文档：

```text
rodski/docs/6.7.6_OLD_CASE_FAILURE_GUIDE.md
```

该文档用于回答“为什么老版本能跑通的用例，在 6.7.6 跑不通”，并给出可执行检查和修改路径。最低内容要求：

1. 用一张总览表列出失败症状、6.7.6 变更原因、检查命令、修复方式。
2. 覆盖以下失败类型：
   - `action="launch"` 在旧包或旧 XSD 下无法校验。
   - 旧 model 简化定位器格式被拒绝。
   - `data.xml` / `data_verify.xml` 不再作为运行时数据源。
   - SQLite 同表行缺字段在 strict 模式下失败。
   - `type` / `verify` 缺字段不再静默跳过。
   - 接口/DB `_verify` 使用 `${Return[-1]}` 被判定为空校验。
   - DB `verify` 不能 0 字段通过。
   - Case XML `data` 中写 `${random(...)}` / `${date(...)}` 被拒绝。
   - `run` 脚本路径从隐式行为切换到规范化解析。
   - wheel/sdist 安装态缺依赖或缺 `schemas/*.xsd` 的排查方式。
3. 每类问题都必须包含“修改前 / 修改后”示例。
4. 给 AI Agent 一个固定检查顺序：
   - 先跑 schema / dry-run；
   - 再检查数据文件组织；
   - 再检查 SQLite schema；
   - 再检查 `_verify` 自引用；
   - 最后检查安装态依赖和 package-data。
5. 明确哪些问题应该修改老用例，哪些问题说明用户安装的是坏包或旧包。
6. 在 release record 中链接该指南。
