# RodSki 长流程规则

长流程、跨角色、端到端、多状态流转，或检查点驱动的 RodSki 用例使用本文。若流程存在多条互斥分支且需要逐条覆盖，考虑用业务模型（见 `business-model.md`）表达分支，长流程规则仍适用于每条路径内部。

## 核心方法

- 编辑 XML 前先画检查点图。每个检查点必须说明角色、平台、业务状态、存储变量和验证模型。
- 保持 case/model/data 三元结构完整。Case 编排检查点，model 定义可观察的 UI/API/DB 字段，data.sqlite 承载输入和期望值。
- 流程不清晰时，不要一次写完整长链路。先构建最小可执行片段，dry-run 后再从最后一个已证明检查点继续扩展。
- 当被测业务路径不要求 UI 预置时，优先使用 API 或 DB 做前置/清理。UI 保留给用户可见状态变化和断言。

## 跨角色会话

- 切换平台或角色前，使用 `close -> navigate -> login -> verify`。
- 不要在同一浏览器会话中跳转到另一个角色的 URL 并假设 cookie 已变化。
- 每次登录后都验证角色特定的落地页标识，而不只是 URL 加载成功。

## 变量

- 对单据编号、流水号、记录 ID 和金额值等需要跨检查点传递的持久业务值使用 `set/get`。
- 避免在长链路中使用脆弱的 `${Return[-N]}` 偏移。只有当生产者和消费者相邻且关系明显时，才在立即相关的数据行内使用 Return。
- 金额值按页面/API 暴露的最小稳定单位存储。当真实业务要求是金额、数量或状态连续性时，不要只比较成功文本。

## 检查点

每个状态转换都应以可观察验证结束：

- 记录创建：验证编号、状态、创建角色和关键金额/数量
- 状态流转（提交、审核、处理、完成等）：验证新状态，以及随状态变化的关键字段
- 跨角色交接：接收方登录后验证能看到同一编号和一致的关键值
- 逆向或取消流程：验证逆向单据编号、类型、状态和金额/数量回退

## 修复失败

- 只修复最新运行证据中的第一个真实失败。
- 重新运行能到达失败检查点的最窄 case、scenario 或 debug plan。
- 如果定位器备用链路很慢，先修复定位器优先级，再考虑增加等待。
- 如果某步骤需要反复固定等待，用面向状态的 `verify`、稳定的就绪定位器，或定向 evaluate 轮询替代。
- 不要用返回固定成功值的宽泛 `evaluate` 掩盖失败检查点。

## 建议工作形态

```text
1. 盘点目标模块
2. 绘制检查点图
3. 识别现有可复用登录/API/DB 模型
4. 为下一个检查点添加或修改最小 model/data 行
5. 串接 case 步骤
6. 运行 guard + data validate + 单 case dry-run
7. 真实运行失败时，诊断结果目录并只修复第一个失败
```
