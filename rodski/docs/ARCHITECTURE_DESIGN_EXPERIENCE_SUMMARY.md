# RodSki 架构设计经验总结

> AI Agent 时代的自动化测试框架，不应该再以“框架自己有多智能”为核心，而应该以“框架能否成为 Agent 稳定可靠的执行底座”为核心。

RodSki 的架构演进，本质上不是一次传统测试框架的功能堆叠，而是一次面向 AI Agent 时代的角色重定义。

传统自动化测试框架通常追求“框架能力完整”：关键字越多越好、内置流程越全越好、平台封装越厚越好、诊断能力越智能越好。但在 AI Agent 时代，这种思路反而可能成为负担。因为 Agent 已经能够承担探索、推理、生成、诊断、修复、选择执行范围等高变化、高认知负载的工作，框架如果继续试图包办这些能力，就会和 Agent 抢职责，最终造成边界混乱、协议复杂、维护困难。

RodSki 最重要的架构取舍是：

> 不把自己做成一个“大而全的智能测试平台”，而是做成 AI Agent 可以稳定依赖的确定性执行引擎与活文档协议层。

也就是说：

```text
Agent 负责思考、探索、决策、生成、修复
RodSki 负责解析、执行、验证、记录、返回结构化结果
```

这条边界，是 RodSki 架构设计中最核心的答案。

## 1. 架构不是画图，而是管理取舍

RodSki 的架构设计首先回答的不是“这个框架看起来够不够先进”，而是：

> 在 AI Agent 时代，自动化测试框架到底应该保留什么能力，又应该把什么能力让给 Agent？

这是一个典型的架构取舍问题。

如果按照传统测试平台思路，RodSki 可以继续做很多事情：

- 内置复杂的用例设计器
- 内置智能规划器
- 内置 Agent 编排框架
- 内置大量业务关键字
- 内置 GUI 测试管理平台
- 内置完整的测试策略系统
- 内置失败自动修复闭环
- 内置自然语言到测试用例的全流程能力

这些方向并不是技术上做不到，而是架构上不一定值得。

RodSki 最终选择的是另一条路：

> 框架只做确定性、稳定性、协议化、可验证的部分；把探索、推理、策略、修复等智能部分交给 AI Agent。

这个取舍背后有几个判断。

第一，Agent 的能力变化很快。如果把 Agent 编排、推理策略、提示词工程、页面探索策略强绑定进 RodSki 核心，框架就会被快速变化的 AI 技术拖着走，稳定性会变差。

第二，测试执行必须确定。AI 可以生成测试意图，但执行层不能“猜”。执行层需要可复现、可调试、可校验。RodSki 因此坚持 XML、SQLite、JSON 这类结构化协议，而不是把自然语言直接作为执行入口。

第三，框架能力越多，Agent 越难正确使用。如果关键字很多、数据引用方式很多、定位器格式很多、输入输出格式很多，Agent 生成错误的概率会显著增加。RodSki 因此持续收敛关键字、收敛定位器格式、收敛数据组织方式。

第四，开发资源应该投入到“Agent 依赖的确定性地基”上。例如 XML Schema、dry-run、结构化结果、统一数据层、plan 预览、错误码、skipped 原因、执行报告，这些能力看起来不如“智能”功能炫，但它们决定了 Agent 能否稳定地调用框架。

所以 RodSki 对架构问题的回答是：

> 架构不是让框架越来越聪明，而是让框架足够可靠，让 Agent 可以放心聪明。

RodSki 牺牲了什么？

- 牺牲了框架自身的“大而全”
- 牺牲了大量内置智能编排能力
- 牺牲了短期看起来更炫的功能展示
- 牺牲了对历史格式的过度兼容
- 牺牲了“什么都能写”的自由度

RodSki 换来了什么？

- 更清晰的职责边界
- 更低的协议歧义
- 更稳定的 Agent 调用接口
- 更容易验证的执行行为
- 更低的长期维护成本
- 更适合自动生成、自动修复、自动回归的测试资产

这就是 RodSki 的第一个架构经验：

> AI Agent 时代的自动化测试框架，不能再以“框架自己有多智能”为核心，而要以“框架能否成为 Agent 稳定可靠的执行底座”为核心。

## 2. 架构首先服务业务边界，而不是技术边界

RodSki 的架构边界不是按技术模块优先划分的，而是按职责认知边界划分的。

它没有把所有能力都塞进一个“智能测试框架”里，而是拆成两个清晰层次：

```text
Layer 1: rodski
确定性执行引擎、XML 协议、数据解析、关键字执行、驱动适配、结果输出

Layer 2: rodski-agent
需求分析、页面探索、用例生成、执行诊断、智能修复、Pipeline 编排
```

这不是简单的代码分层，而是业务能力分层。

RodSki 的核心业务能力不是“生成测试用例”，而是：

> 把结构化测试意图稳定执行出来，并返回可被 Agent 理解的结果。

rodski-agent 的核心业务能力才是：

> 从需求、页面、失败结果中做判断，并生成或修复测试资产。

这两个边界如果混在一起，架构会很快失控。假设 RodSki 核心引擎直接内置 Agent 规划能力，会出现几个问题：

- 执行引擎会依赖 LLM 服务，稳定性下降
- CLI 结果会混入推理过程，确定性下降
- 单元测试和验收测试会变复杂
- 用户无法只使用执行引擎
- 外部 Agent 难以替换 RodSki 内置 Agent
- 框架会从“工具”变成“平台”，边界变重

RodSki 选择了相反方向：

```text
外部 Agent / rodski-agent
        |
        | 生成 XML / SQLite / plan
        v
RodSki CLI
        |
        | 解析协议并执行
        v
Driver / API / DB / Vision Locator
        |
        | 返回 JSON / XML / report / screenshots / recordings
        v
Agent 再分析
```

这个边界清晰地回答了“谁负责什么”。

Agent 负责需求理解、页面探索、元素识别、用例设计、测试数据设计、失败诊断、修复策略、执行范围选择、报告解读。

RodSki 负责 XML 解析、model / case / data / plan 协议校验、关键字执行、跨平台驱动适配、数据引用解析、Return / 变量传递、批量输入与验证、结构化结果输出、dry-run 与 preview、报告与执行证据记录。

这个边界的价值在于：

> Agent 的变化不会污染执行引擎，执行引擎的稳定性也不会限制 Agent 的进化。

RodSki 在关键字设计上也体现了这种边界意识。

它没有无限扩展业务动作关键字，而是将核心能力收敛为：

```text
type   -> UI 批量输入
send   -> API 请求发送
verify -> UI / API / DB 批量验证
run    -> 脚本扩展逃生舱
navigate / launch -> 应用或页面启动
```

尤其是 API 测试，RodSki 没有设计 `http_get`、`http_post`、`assert_status`、`assert_json` 等一堆细碎关键字，而是统一为：

```text
send + verify
```

这个选择非常重要。

因为 Agent 生成测试用例时，最怕面对一堆近义关键字。关键字越多，Agent 越容易生成不一致、不稳定、难维护的 XML。RodSki 通过关键字收敛，把复杂性转移到 model / data 的结构化表达中，让 Agent 只需要学习少量稳定动作。

同样，UI 原子动作也不作为 Case XML 的 action 出现。比如：

```text
click
hover
select
scroll
key_press
drag
```

这些动作不直接变成测试步骤关键字，而是作为数据字段值由 `type` 批量模式解释执行。

这背后的架构判断是：

> Case XML 应表达测试流程，Data 层表达操作细节，Model 层表达定位知识。不要让步骤层变成低级 UI 操作流水账。

所以 RodSki 的第二个架构经验是：

> 自动化测试框架的边界，不应该按“我能封装哪些技术动作”来划分，而应该按“Agent、测试资产、执行引擎各自承担什么认知责任”来划分。

边界划对了，后面的技术选型才有意义。

## 3. 架构要面向变化，而不是面向当下需求

RodSki 的演进过程中，一个很重要的设计原则是：

> 对容易变化的部分保持开放，对必须稳定的部分强约束。

AI Agent 时代，变化最快的部分包括：

- LLM 模型能力
- 页面探索策略
- 视觉识别方案
- 用例生成策略
- 失败修复策略
- 测试计划选择策略
- 用户对调试粒度的要求
- Web / Mobile / Desktop 场景组合

变化较慢、必须稳定的部分包括：

- XML 协议
- 数据引用规则
- 模型与数据的对应关系
- 关键字语义
- CLI 输入输出契约
- 错误码与结果结构
- 执行证据格式
- dry-run / validate / preview 语义

RodSki 的架构策略，是把变化快的东西放到 Agent 或可选能力层，把变化慢的东西沉淀成协议。

例如视觉能力就是一个典型例子。

视觉定位可以不断演进：模板匹配、OCR、OmniParser、多模态 LLM、坐标识别、语义元素识别。但 RodSki 没有因此新增一堆视觉关键字，比如：

```text
vision_click
ocr_click
ai_find
llm_assert
```

而是把视觉能力收敛为定位器类型：

```xml
<location type="vision">img/login_btn.png</location>
<location type="ocr">登录</location>
<location type="vision_bbox">100,200,150,250</location>
```

也就是说，变化的是“怎么定位”，稳定的是“元素仍然通过 model.xml 表达，执行仍然通过 type / verify 完成”。

这是一个很关键的架构取舍：

> 视觉能力是定位能力的增强，不是测试流程语义的扩张。

同样，测试数据从 XML 演进到 SQLite 时，RodSki 没有改变 Case 的写法：

```xml
<test_step action="type" model="Login" data="L001"/>
<test_step action="verify" model="Login" data="V001"/>
```

SQLite 只是数据承载方式的变化，不应该改变测试语义。Case 仍然只写 DataID，模型名仍然对应逻辑表名，verify 仍然自动查找 `{ModelName}_verify`。

这个设计保护了测试资产的稳定性，也降低了 Agent 的学习成本。

RodSki 在 v6.3 规划中引入 scenario / plan / selector / debug plan，也体现了“面向变化”的设计。

随着用例越来越复杂，用户和 Agent 都需要更细粒度地选择执行范围。传统做法可能是直接在 case XML 中频繁修改 `execute="是/否"`，或者让 Agent 直接改用例文件。但这会带来风险：

- Agent 为了调试临时修改 case XML，可能污染正式测试资产
- 执行范围和测试定义混在一起，难以追踪
- 想执行某个 scenario 或 step 时，需要侵入性修改 XML
- 多个计划、多个场景、多个调试目标之间难以管理

RodSki 的设计选择是引入独立的 `plan/*.xml`：

```text
case XML 负责定义测试事实
plan XML 负责定义本次执行选择
selector 负责生成临时执行选择
debug plan 负责表达调试意图
```

这背后的架构思想是：

> 测试资产定义和执行选择应该分离。

这样 Agent 可以安全地创建、预览、校验、执行 plan，而不是直接篡改 case/model/data。调试能力也从“修改用例”变成“生成调试计划”。

RodSki 没有提前把所有未来需求都硬编码进核心流程，而是给变化留出位置：

- 普通执行用 case
- 执行选择用 plan
- 临时筛选用 selector
- 调试执行用 debug plan
- 不可覆盖场景用 run 脚本
- 可选智能能力放在 vision / llm / rodski-agent

所以 RodSki 的第三个架构经验是：

> 面向 AI Agent 的框架，不是提前内置所有智能功能，而是提前设计稳定协议，让未来的 Agent 能以低成本接入、选择、修复和扩展。

好的架构不是永远不变，而是知道哪些地方必须稳定，哪些地方必须允许变化。

## 4. 架构必须把复杂性关进笼子

自动化测试框架天然复杂。

RodSki 面对的复杂性包括：

- Web / Mobile / Desktop 多平台差异
- UI / API / DB 多测试类型差异
- 传统定位 / 视觉定位 / OCR / 坐标定位差异
- 输入数据 / 验证数据 / 全局变量 / Return 变量差异
- case / scenario / step / plan / selector 的执行层级差异
- Agent 生成 XML 时的语法漂移风险
- 失败诊断、截图、录屏、报告、重试带来的链路复杂性

这些复杂性不能靠“多写几个 if”解决。RodSki 的核心策略是：

> 把复杂性关进协议、层次和少量稳定概念里。

### 4.1 把动作复杂性关进关键字体系

RodSki 不让关键字无限膨胀，而是用少量核心关键字覆盖大部分行为：

```text
type   -> UI 输入与 UI 原子动作批量执行
send   -> API 请求
verify -> UI / API / DB 验证
run    -> Python 脚本扩展
```

这样，Agent 生成用例时，不需要在几十个动作关键字中选择。它只需要决定：

- 这是 UI 操作吗？用 `type`
- 这是接口请求吗？用 `send`
- 这是验证吗？用 `verify`
- 内置能力不够吗？用 `run`

### 4.2 把定位复杂性关进 model.xml

元素怎么找，是传统 CSS、XPath、文本、OCR、图片、坐标，都不应该污染 Case XML。Case XML 只表达：

```xml
<test_step action="type" model="Login" data="L001"/>
```

具体字段对应哪个元素、元素有哪些定位器、定位器优先级如何，全放在 model.xml。

这样做有两个好处：

- 测试流程不会因为定位策略变化而频繁变动
- Agent 修复定位器时，只需要更新 model，不需要重写 case

### 4.3 把数据复杂性关进 data.sqlite 和 globalvalue.xml

RodSki 坚持模型名与逻辑表名一致，元素名与字段名一致，verify 自动找 `_verify` 表。这些规则看起来严格，但它们减少了歧义。

如果允许：

```text
model 名和数据表名随便映射
case 里既可以写 DataID，也可以写 Model.DataID
verify 表可以随便命名
Return 可以在任意位置引用
```

短期看似灵活，长期一定会变成 Agent 和人都难以维护的复杂系统。

RodSki 的选择是：

> 宁可约束强一点，也不要让协议出现多种等价写法。

### 4.4 把执行选择复杂性关进 plan

case 是测试事实，plan 是执行意图。这个边界能显著降低复杂性。

例如：

```text
我要全量跑
我要只跑 smoke
我要跳过 slow
我要调试某个 scenario
我要只从某个 step 开始跑
我要保留现场不 cleanup
```

这些都不是 case 本身的业务定义，而是“本次怎么执行”。如果都塞回 case XML，case 会越来越脏。RodSki 用 plan / selector / debug plan 把它们隔离出去。

### 4.5 把不可预测复杂性关进 run

任何测试框架都会遇到内置关键字无法覆盖的情况。RodSki 没有为每个特殊场景新增专用关键字，而是保留 `run` 作为脚本逃生舱。

这也是一个重要取舍：

> 不要为了少数特殊场景污染通用协议。特殊复杂性应该被隔离在脚本里，而不是扩散到关键字系统。

### 4.6 把 AI 复杂性关到 Agent 层或可选能力层

LLM 判断、视觉语义识别、失败诊断、智能修复都很有价值，但不能成为核心执行链路的前提。RodSki 的核心执行必须在没有 LLM 的情况下仍然成立。

AI 能力可以增强 RodSki，但不能绑架 RodSki。

所以 RodSki 的第四个架构经验是：

> 框架不是通过增加功能消灭复杂性，而是通过稳定边界、唯一协议和清晰层次限制复杂性的传播。

一个适合 Agent 的框架，最怕的不是功能少，而是歧义多。歧义越多，Agent 生成、修复、调试的成本越高。

## 5. 架构是社会技术系统，不只是代码系统

RodSki 的架构选择也不是纯技术判断，而是考虑了团队能力、维护成本、使用方式和 AI Agent 协作模式。

如果一个小团队要维护一个高度智能化、全平台、全功能、内置 Agent 编排、内置 UI 管理、内置诊断平台的测试系统，长期成本会非常高。

RodSki 的现实判断是：

> 团队应该把有限精力投入到最能形成长期价值的地方：协议、执行、数据、结果、验证和文档约束。

这也是为什么 RodSki 特别重视文档契约。

在传统框架里，文档不一致主要影响人。但在 Agent 时代，文档不一致会直接影响机器生成结果。

如果 README 写一种格式，核心约束写另一种格式，示例里又出现旧格式，Agent 很可能学错并持续生成错误 XML。

所以 RodSki 的架构治理必须包括：

- 核心设计约束
- 用例编写指南
- 数据文件组织规则
- Agent 集成指南
- XSD Schema
- demo 验收用例
- dry-run 校验
- CLI 结构化输出
- 错误码和错误信息

这些不是“附属文档”，而是 Agent 时代框架架构的一部分。

RodSki 的文档、Schema、CLI、demo、测试共同构成一个契约系统：

```text
文档告诉 Agent 应该怎么写
Schema 限制 Agent 不能乱写
dry-run 提前发现错误
run 执行确定性动作
JSON 结果让 Agent 可解析
demo 证明协议真的可跑
```

这就是社会技术系统的体现。

RodSki 还主动避免把团队拖入过重的平台化建设。

当前 rodski-agent 可以提供 design / run / pipeline / diagnose 等能力，但 RodSki 核心不把自己绑定成某个 Agent 框架。它可以被 Claude Code 调用，也可以被 CI 调用，也可以被未来的专用 Agent 调用，也可以被人手写 XML 调用。

这种开放性降低了组织风险：

- 不押注单一 Agent 框架
- 不要求用户必须采用某个 LLM provider
- 不把执行引擎和智能编排绑死
- 不让测试资产依赖某个对话系统
- 不阻碍未来接入更多 Agent 工具链

所以 RodSki 的第五个架构经验是：

> AI Agent 时代的架构，不只是代码如何分层，还包括人、Agent、文档、协议、CLI、测试资产之间如何协作。

如果团队无法长期驾驭一个架构，再先进也没有意义。RodSki 的取舍，是让核心系统保持小而硬，把高变化的智能协作放到外层。

## 6. AI Agent 时代的自动化测试框架应该是什么样子的

结合 RodSki 的实践，可以总结出一个判断：

> AI Agent 时代的自动化测试框架，不应该再以“内置多少测试能力”为第一目标，而应该以“是否能被 Agent 稳定生成、稳定执行、稳定诊断、稳定修复”为第一目标。

这样的框架应该具备几个特征。

### 6.1 输入必须结构化

Agent 可以理解自然语言，但执行层不能直接依赖自然语言。自然语言适合表达需求，不适合作为确定性执行协议。

RodSki 选择 XML / SQLite / plan，是因为它们具备：

- 可读
- 可写
- 可校验
- 可 diff
- 可版本管理
- 可被 Agent 生成
- 可被 Schema 约束
- 可被 dry-run 验证

所以理想形态是：

```text
自然语言需求 -> Agent 理解 -> 生成结构化测试资产 -> 框架执行
```

而不是：

```text
自然语言需求 -> 框架直接猜测执行
```

### 6.2 协议必须少歧义

Agent 最怕多种等价写法。例如：

- 同一个定位器有三种格式
- 同一个数据引用有多种写法
- 同一个 API 请求可以用多个关键字表达
- 同一个验证可以写在 case、data、assert、verify 多个地方
- 同一个执行范围既能改 case，又能改 plan，又能传 CLI 参数

这些都会让 Agent 生成不稳定。

RodSki 的方向是：

> 保留一种主路径，旧路径逐步废弃或迁移，不让兼容性吞掉协议清晰度。

### 6.3 框架要返回 Agent 能理解的结果

传统测试报告面向人阅读，Agent 时代的结果还必须面向机器消费。

所以结果应该包含：

- 总数、通过、失败、跳过
- case / scenario / step 层级
- 明确失败原因
- 错误类型
- 错误码
- 关联截图
- 关联录屏
- Return 值
- skipped 原因
- 执行耗时
- 可定位到具体测试资产的位置

RodSki 的 `--output-format json`、execution summary、report、recording_path、dry-run preview 都是在往这个方向演进。

### 6.4 框架应该支持 Agent 安全试错

Agent 生成的测试资产不可能一次完全正确，所以框架必须提供安全反馈机制：

- validate
- dry-run
- explain
- plan preview
- data schema
- data show
- clear error message
- stale reference 检查
- debug plan

这些能力不是锦上添花，而是 Agent 工作流的基础设施。

Agent 需要不断循环：

```text
生成 -> 校验 -> 执行 -> 分析 -> 修复 -> 再执行
```

框架必须让这个循环低成本、可控、可观察。

### 6.5 框架应该允许 Agent 改“外围”，少改“核心资产”

例如执行范围应该通过 plan 表达，而不是让 Agent 频繁修改 case XML 的执行开关。调试某个步骤应该通过 debug plan，而不是让 Agent 临时删除前后步骤。定位器修复应该优先修改 model，而不是重写用例流程。

这背后的原则是：

> Agent 可以频繁试错，但测试资产的核心事实不能被频繁污染。

### 6.6 框架应该保留扩展逃生舱，但不能让逃生舱变成主路径

RodSki 的 `run` 是必要的，因为真实测试世界总有特殊逻辑。但如果大量能力都依赖 `run`，说明协议设计不够稳定。

所以 `run` 应该是扩展点，不是常规测试表达方式。

### 6.7 框架应该“够用”，而不是“全能”

AI Agent 时代，框架不需要内置所有高级判断。很多判断交给 Agent 更合适：

- 哪些用例应该生成
- 页面上哪个元素是登录按钮
- 失败是数据问题还是定位问题
- 应该优先修复 model 还是 data
- 哪些 scenario 适合 smoke
- 本次回归应该跑哪些计划
- 报告中的失败是否是环境问题

框架只需要提供足够清晰的工具和反馈，让 Agent 能做这些判断。

所以 RodSki 的定位可以总结为：

> 不做 Agent 的大脑，做 Agent 的手、眼、账本和规则边界。

手：执行测试动作。  
眼：提供截图、录屏、结果、日志。  
账本：记录结构化结果和测试证据。  
规则边界：用 XML / SQLite / XSD / CLI 契约约束输入输出。

## 7. 为什么不是让 AI 直接生成 Playwright 测试代码

在 AI Agent 时代，一个非常自然的问题是：

> 既然 AI 已经能写代码，为什么不让 AI 直接生成 Playwright、Appium、Pytest、Selenium 等测试代码，而要设计 RodSki 的 XML 活文档协议和确定性执行引擎？

这个问题本质上也是一个架构取舍。

让 AI 直接生成测试代码，短期看起来非常高效：

- 不需要设计 DSL 或 XML 协议
- 不需要维护关键字引擎
- 不需要维护 case / model / data 三元结构
- AI 可以直接调用 Playwright、Appium、requests、pytest 等成熟工具
- 对少量一次性测试任务，上手速度很快

但 RodSki 没有把这条路作为主架构方向，原因不是“AI 不能写代码”，而是“测试资产长期治理不应该完全等同于代码生成”。

### 7.1 直接生成代码的问题

AI 直接生成测试代码的问题，通常不是第一版跑不起来，而是长期会变得难以治理。

第一，代码自由度太高，生成结果不稳定。  
同一个登录测试，AI 可以生成很多种 Playwright 写法：

```python
page.fill("#username", "admin")
page.get_by_label("用户名").fill("admin")
page.locator("input[name='username']").fill("admin")
page.get_by_role("textbox").nth(0).fill("admin")
```

这些写法都可能正确，但风格、抽象、等待策略、错误处理、数据组织方式不一致。对人来说这是代码风格问题，对 Agent 来说这是长期维护问题。

第二，测试意图和技术实现混在一起。  
当 AI 直接生成 Playwright 代码时，测试流程、元素定位、测试数据、断言逻辑、等待策略、异常处理、调试输出经常混在一个脚本里。短期能跑，长期难以回答：

- 这个测试到底验证什么业务意图？
- 哪些是测试数据，哪些是页面定位？
- 定位器变化时要改哪里？
- 数据变化时是否需要改代码？
- 失败是业务失败、数据失败、定位失败，还是脚本实现失败？
- Agent 修复时应该改 locator、data、assertion，还是流程？

RodSki 把这些东西拆成 case / model / data / plan，是为了让测试资产的不同变化维度可被单独管理。

第三，代码生成容易产生隐性复杂性。  
AI 生成代码时，可能为了让当前任务跑通而引入局部技巧：

- 临时 `sleep`
- 随机重试
- 宽松断言
- 动态拼接选择器
- 在脚本中硬编码账号、URL、token
- 捕获异常后继续执行
- 把页面探索逻辑和正式测试逻辑混在一起

这些写法短期提升成功率，长期会降低测试可信度。

第四，跨平台一致性难以保证。  
Playwright、Appium、PyWinAuto、requests、DB driver 的编程模型不同。如果让 AI 直接生成代码，Web、Mobile、Desktop、API、DB 测试会自然分裂成多套代码风格。RodSki 选择用 `type/send/verify/run` 收敛上层语义，就是为了让不同平台在测试资产层保持一致。

第五，代码评审成本高于协议校验成本。  
XML / SQLite / plan 可以通过 XSD、dry-run、data validate、plan preview 做结构化校验。  
而 AI 生成的 Python/TypeScript 测试代码，即使语法正确，也不代表：

- 等待策略合理
- 断言足够严格
- 数据没有硬编码
- 定位器可维护
- 异常没有被吞掉
- 没有引入危险副作用

也就是说，代码能运行不等于测试资产是可靠的。

第六，Agent 修复代码的边界更模糊。  
当测试失败时，Agent 如果面对的是一段自由代码，它可以改任何地方。这个能力很强，但风险也很高。它可能为了让测试通过而弱化断言、绕过步骤、改掉业务检查。  
如果面对的是 RodSki 的结构化资产，Agent 的修复空间更清晰：

- 定位失败，优先修复 model.xml
- 数据错误，优先修复 data.sqlite
- 预期不对，优先修复 `_verify` 表
- 流程选择问题，优先修复 plan
- 内置关键字覆盖不了，才使用 `run`

这种约束不是为了限制 Agent，而是为了让 Agent 的修复更可解释、更可审计。

### 7.2 RodSki 不是否定 Playwright，而是把 Playwright 放在正确层次

RodSki 并不是不用 Playwright。相反，RodSki 的 Web 执行能力正是建立在 Playwright 这类成熟工具之上。

关键区别是：

```text
AI 直接生成 Playwright 代码：
需求 -> Agent -> Playwright/Pytest 脚本 -> 执行

RodSki 的方式：
需求 -> Agent -> XML / SQLite / plan -> RodSki -> Playwright/Appium/PyWinAuto/API/DB -> 结构化结果
```

也就是说，Playwright 在 RodSki 架构里是底层执行驱动，而不是测试资产的主要表达语言。

这个分层带来的价值是：

- Agent 不需要掌握每个平台的全部 API 细节
- 测试资产不直接绑定某个底层工具
- Web、Mobile、Desktop、API 可以共享上层测试语义
- 底层驱动可以演进，上层 case / model / data 尽量稳定
- 结果输出可以统一成 Agent 可解析的结构

所以 RodSki 的取舍不是：

```text
XML 好，Playwright 不好
```

而是：

```text
Playwright 适合作为执行能力
XML / SQLite / plan 更适合作为长期测试资产协议
```

### 7.3 什么情况下可以让 AI 直接生成测试代码

RodSki 并不否认 AI 直接生成代码的价值。以下场景下，直接生成 Playwright / Pytest / requests 代码是合理的：

- 一次性探索验证
- 临时 POC
- 快速复现问题
- 业务流程还没有稳定下来
- 团队只需要少量脚本，不需要长期维护
- 某个特殊场景明显超出 RodSki 内置协议表达能力

这些场景下，代码生成的灵活性比资产治理更重要。

RodSki 也为特殊场景保留了 `run` 脚本能力。也就是说，当结构化协议覆盖不了时，可以用代码作为逃生舱。

但 RodSki 不把“直接生成任意测试代码”作为主路径，因为主路径要服务的是长期可维护的测试资产，而不是一次性脚本。

### 7.4 什么情况下应该使用 RodSki 协议

当目标是长期维护、持续回归、多人协作、Agent 自动生成和自动修复时，RodSki 的协议化方式更合适。

典型场景包括：

- 测试资产需要长期沉淀
- 用例需要被人和 Agent 共同理解
- 数据、定位器、流程需要分开维护
- 失败结果需要结构化分析
- 需要 Web / Mobile / Desktop / API / DB 多类型统一
- 需要 dry-run / validate / preview 等安全反馈
- 需要 Agent 在受控边界内自动修复
- 需要 CI 中稳定执行和统一报告

这些场景下，直接生成代码的自由度反而会成为长期成本。

### 7.5 这条取舍的本质

RodSki 的判断是：

> AI 可以生成代码，但自动化测试资产不应该只是一堆 AI 生成的代码。

代码是强大的执行表达，但不是最适合 Agent 长期治理的资产协议。

RodSki 选择 XML / SQLite / plan，不是为了绕开 Playwright，而是为了把测试系统拆成更稳定的层次：

```text
需求层：自然语言，适合人和 Agent 沟通
协议层：XML / SQLite / plan，适合沉淀测试资产
执行层：RodSki keyword engine，适合确定性调度
驱动层：Playwright / Appium / PyWinAuto / API / DB，适合执行具体动作
分析层：Agent，适合诊断、修复、决策
```

这条分层的核心收益是：

- 让 AI 的创造力停留在合适的位置
- 让测试资产有稳定形态
- 让底层工具保持可替换
- 让执行结果可验证、可追踪、可解释
- 让 Agent 修复有边界，而不是任意改代码

所以 RodSki 不选择“AI 直接生成 Playwright 测试代码”作为主架构，不是因为这条路不能用，而是因为它更适合短期脚本和探索任务；RodSki 要解决的是长期测试资产的协议化、确定性执行和 Agent 可治理问题。

一句话总结：

> 直接生成 Playwright 代码，解决的是“让 AI 快速写出一个能跑的测试”；RodSki 解决的是“让 AI 持续维护一套可验证、可演进、可审计的测试资产”。

## 8. RodSki 的核心架构取舍

| 架构问题 | RodSki 的选择 | 放弃了什么 | 换来了什么 |
|---|---|---|---|
| 框架定位 | 确定性执行引擎 + 活文档协议层 | 大而全智能测试平台 | 职责清晰、稳定可集成 |
| Agent 边界 | Agent 负责思考，RodSki 负责执行 | 框架内置完整 Agent 编排 | 可被不同 Agent 调用 |
| 测试资产表达 | XML / SQLite / plan 活文档协议 | AI 直接生成任意 Playwright 等测试代码作为主路径 | 测试意图、定位器、数据、执行计划可分层治理 |
| 输入协议 | XML / SQLite / plan 结构化输入 | 自然语言直接执行 | 可校验、可追踪、可版本化 |
| 关键字体系 | 收敛核心关键字 | 大量细碎动作关键字 | Agent 更容易生成正确用例 |
| API 测试 | send + verify | http_get/http_post/assert_json 等关键字 | 协议统一、语义简单 |
| UI 动作 | 原子动作进入 data，由 type 批量执行 | case 中直接写 click/hover/scroll | 流程层更干净 |
| 视觉能力 | 作为 locator type | 新增视觉专用关键字 | 测试语义稳定 |
| 数据层 | 模型名、逻辑表名、字段名强一致 | 灵活映射 | 少歧义、易校验 |
| 执行选择 | plan / selector / debug plan | 直接频繁修改 case | 保护测试资产 |
| 特殊能力 | run 脚本逃生舱 | 为每个场景新增关键字 | 控制关键字膨胀 |
| 智能能力 | 放在 rodski-agent 或可选能力层 | 核心引擎依赖 LLM | 核心可稳定运行 |
| 文档治理 | 文档 + XSD + demo + dry-run 共同约束 | 仅靠代码约定 | Agent 不容易学错 |

这张表背后的本质是：

> RodSki 一直在做减法。不是减少能力，而是减少歧义、减少耦合、减少 Agent 使用框架时的决策成本。

## 9. RodSki 对五个架构问题的回答

### 9.1 这个系统最重要的质量属性是什么？

RodSki 最重要的质量属性不是“智能程度”，而是：

- 确定性
- 可验证性
- 协议稳定性
- Agent 可生成性
- Agent 可解析性
- 跨平台执行一致性
- 测试资产可维护性

RodSki 的核心用户不只是人，也是 AI Agent。所以它的质量属性必须包括“机器可理解”和“机器可稳定操作”。

### 9.2 为了满足这些质量属性，牺牲了什么？

RodSki 牺牲了部分灵活性和短期功能丰富度。

例如：

- 不鼓励多套定位器格式
- 不鼓励 case 中直接写原子 UI 动作
- 不设计大量 HTTP 关键字
- 不把 Agent 编排塞进核心引擎
- 不把所有智能能力做成核心依赖
- 不为了兼容旧写法长期保留多套语义

这些牺牲看起来会让框架“没那么自由”，但正是这些约束让 Agent 能稳定生成和维护测试资产。

### 9.3 这个牺牲现在值得吗？

值得。

因为 RodSki 面向的是 AI Agent 时代的自动化测试，不是传统的手写脚本时代。

在手写脚本时代，灵活性对人很重要；在 Agent 生成时代，协议一致性比灵活性更重要。

Agent 不怕规则严格，Agent 怕规则含糊。

只要规则清晰、反馈明确、错误可修复，Agent 可以很好地适应强约束协议。反过来，如果框架过度灵活、写法太多，Agent 会不断生成边缘格式、历史格式和混合格式，维护成本会迅速上升。

### 9.4 如果以后判断错了，能不能改？

RodSki 通过分层和协议隔离降低了未来修改成本。

例如：

- LLM 能力在 rodski-agent 或可选能力层，可以替换
- 视觉定位是 locator type，可以扩展
- 数据承载从 XML 到 SQLite，不改变 case 语义
- 执行选择通过 plan 扩展，不污染 case
- 特殊能力通过 run 承接，不破坏关键字体系
- CLI / JSON 契约可以被外部 Agent 复用

这说明 RodSki 的很多架构决策是可演进的，而不是一次性押注。

### 9.5 这个团队能不能长期驾驭这个架构？

RodSki 的架构选择本身就在降低团队长期负担。

它没有把自己做成一个包含 Agent Runtime、UI 平台、测试管理平台、智能诊断平台、视觉平台的巨型系统，而是把核心收敛为：

```text
协议 + 执行 + 数据 + 结果 + 校验
```

这更符合小团队或快速演进项目的现实。

团队不需要追着所有 Agent 框架变化跑，只需要保证 RodSki 作为执行底座稳定可靠。未来无论外部 Agent 是 Claude Code、LangGraph、AutoGen、CrewAI、自研系统，还是 CI 中的脚本，都可以通过 RodSki 的 CLI 和协议接入。

这就是可长期驾驭的架构。

## 10. 一句话总结

如果只用一句话概括 RodSki 的架构经验，可以是：

> 在 AI Agent 时代，自动化测试框架的核心价值不是替 Agent 思考，而是用稳定协议、确定性执行和可验证结果，成为 Agent 可以长期依赖的测试执行底座。

再短一点：

> Agent 负责智能，RodSki 负责确定性。

这句话背后不是简单分工，而是一整套架构取舍：

- 把智能让给 Agent
- 把协议留给框架
- 把变化放到外层
- 把确定性沉到底层
- 把复杂性关进 model / data / plan / result
- 把测试资产变成 Agent 可读、可写、可校验、可执行的活文档

## 11. 后续可继续补充的案例

这份总结后续可以继续补充几个更具体的 RodSki 案例：

1. RodSki 从旧数据 XML 到 SQLite 的真实取舍过程  
   展开“数据承载方式变化，但 Case 语义不变”的架构价值。

2. 为什么 RodSki 坚持 `type/send/verify` 收敛关键字  
   对比传统关键字驱动框架，说明 Agent 生成稳定性为什么比关键字丰富度更重要。

3. 为什么视觉定位不是新关键字，而是 locator type  
   作为“把变化关进合适抽象”的代表案例。

4. 为什么要引入 plan，而不是继续用 case 的 `execute` 控制执行范围  
   作为“测试事实”和“执行意图”分离的代表案例。

5. rodski-agent 和 rodski 的边界是否还要继续收紧  
   继续讨论 LLM 能力、诊断能力、视觉能力到底哪些应该在 core，哪些应该在 agent 层。

6. README、核心约束、Agent 文档之间的契约一致性  
   Agent 时代文档不一致会直接导致生成错误，这一点可以作为“文档也是架构”的案例展开。

## 12. 结语

RodSki 的架构实践说明，AI Agent 时代的自动化测试框架不应该急着把自己做成“更聪明的测试平台”。真正重要的是重新划分智能系统和确定性系统的边界。

Agent 擅长理解需求、探索页面、生成用例、诊断失败、调整策略；框架擅长执行协议、约束格式、驱动平台、记录证据、返回结果。当框架主动给 Agent 让道，只保留稳定、必要、可验证的能力时，整个系统反而更容易演进。

RodSki 的价值不在于替代 Agent，而在于让 Agent 有一个可靠的落脚点。

最终，好的 AI 自动化测试架构应该是：

```text
需求可以自然语言表达
测试资产必须结构化沉淀
执行过程必须确定可复现
失败结果必须可诊断
修复动作必须可验证
智能能力必须可替换
核心协议必须长期稳定
```

这也是 RodSki 当前架构设计最重要的经验。
