## 一、技术路线全景图

UI Agent 在 2024-2026 这两年快速分化，目前形成**三条主要技术路线**和一条**融合路线**。

```

│                    UI Agent 技术路线                         │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│   路线 A: 结构化感知 (DOM/AX Tree)                           │
│   ├─ Web:    Browser-Use, Stagehand, Playwright MCP         │
│   └─ Mobile: mobile-use, mobile-mcp                          │
│                                                              │
│   路线 B: 纯视觉感知 (Vision-Only)                           │
│   ├─ Web:    OpenAI CUA, Anthropic Computer Use             │
│   └─ Mobile: AppAgent, MobileAgent, OmniParser              │
│                                                              │
│   路线 C: 混合感知 (Hybrid)                                  │
│   ├─ Web:    Browser-Use (DOM + 截图双模态)                  │
│   └─ Mobile: mobile-use (Tree + 截图)                        │
│                                                              │
│   路线 D: 端到端视觉模型 (E2E Vision Model)                  │
│   ├─ SeeClick, CogAgent, ShowUI                              │
│   └─ 直接输出坐标，无需中间表示                              │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

## 二、四条路线深度对比

### 2.1 路线 A：结构化感知（DOM / Accessibility Tree）

**原理**：通过协议层（CDP / UIAutomator2 / XCUITest）直接获取 UI 的结构化表示，序列化为文本喂给 LLM。

```
浏览器/App → 协议层 → XML/JSON 结构 → 文本序列化（带 index）
  → LLM（文本模型即可，不一定需要视觉）
  → 输出 index → 反查节点 → 执行
```

**代表项目**：Browser-Use、Stagehand、Playwright MCP、mobile-use

**优点**：
- **精度高**：基于真实节点 ID，定位 100% 准确
- **速度快**：文本序列化只需几十 ms
- **成本低**：可用纯文本模型（GPT-4o-mini、Claude Haiku）
- **可解释**：每个 action 对应明确的节点，调试容易

**缺点**：
- **依赖 Tree 质量**：Flutter/React Native/游戏/Canvas Tree 为空或残缺
- **跨平台代码不可见**：很多现代 App 用自定义渲染，Tree 看不到真实控件
- **iframe / Shadow DOM 复杂**：需要深度遍历

---

### 2.2 路线 B：纯视觉感知（Vision-Only）

**原理**：完全不用结构化数据，只截图 → 视觉模型理解 → 输出坐标。

```
截图 → 多模态 LLM（GPT-4V / Claude Sonnet / Qwen-VL）
  → LLM 输出像素坐标 (x, y)
  → 直接坐标点击
```

**代表项目**：OpenAI Computer Use Agent (CUA)、Anthropic Computer Use、AppAgent

**优点**：
- **通用性极强**：任何能渲染像素的界面都能操作（游戏、桌面、远程虚拟机）
- **不依赖底层协议**：无需 CDP、Appium，只要能截图
- **跨平台一致**：Web/Mobile/Desktop 同一套逻辑

**缺点**：
- **坐标不稳定**：分辨率变化、滚动、动画都会让坐标失效
- **慢**：视觉模型推理 2-5 秒/步
- **贵**：视觉 token 是文本的 10-100 倍
- **小元素困难**：视觉模型对小图标、密集列表识别差
- **精度天花板**：当前最强视觉模型坐标精度也只有 ±10 px

---

### 2.3 路线 C：混合感知（Hybrid）

**原理**：同时给 LLM 提供结构化 Tree 文本 + 截图，互相校验。

```
DOM/Tree 文本（带 index）+ 截图 → 多模态 LLM
  → LLM 输出 index（首选）或坐标（兜底）
  → 反查节点或直接坐标执行
```

**代表项目**：Browser-Use（成熟实现）、mobile-use

**优点**：
- **鲁棒性最强**：Tree 失效时用视觉，视觉模糊时用 Tree
- **精度 + 通用**：兼顾两者优点
- **自愈能力**：Tree 节点位置变了，视觉能纠偏

**缺点**：
- **Token 消耗大**：文本 + 图像同时发送
- **实现复杂**：需要双通道融合逻辑
- **延迟叠加**：Tree 序列化 + 截图编码

---

### 2.4 路线 D：端到端视觉模型（E2E Vision Grounding）

**原理**：专门微调的视觉模型，直接从截图 + 任务描述输出坐标，跳过通用 LLM。

```
截图 + "点击登录按钮" → 微调的 Vision Grounding 模型
  → 直接输出 (x, y) 或 bounding box
  → 执行点击
```

**代表项目**：
- **SeeClick**（南大）：第一个 GUI grounding 专用模型
- **CogAgent**（清华）：18B 参数，专为 GUI 设计
- **ShowUI**（新加坡国立）：2B 轻量级
- **OmniParser**（微软）：截图 → 元素列表 + 标签
- **UI-TARS**（字节）：基于 Qwen2-VL，开源

**优点**：
- **专门优化**：远比通用 LLM 在 GUI 任务上准
- **快**：小模型推理 100-500 ms
- **可本地部署**：2B-7B 模型能跑在单卡 GPU

**缺点**：
- **泛化弱**：训练数据外的界面准确率骤降
- **生态早期**：工具链、调用方式不成熟
- **需要 GPU**：本地部署门槛高

## 四、视觉识别技术现状（2026-05）

### 4.1 通用多模态模型 GUI 能力

| 模型 | GUI 定位精度 | 推理速度 | 价格（输入/输出 per 1M tokens） |
|------|------------|---------|------------------------------|
| GPT-4o | ★★★★ | 2-4s | $2.5 / $10 |
| GPT-4o-mini | ★★★ | 1-2s | $0.15 / $0.6 |
| Claude Opus 4.7 | ★★★★★ | 3-5s | $15 / $75 |
| Claude Sonnet 4.6 | ★★★★ | 1-3s | $3 / $15 |
| Claude Haiku 4.5 | ★★★ | 0.5-1s | $1 / $5 |
| Gemini 2.5 Pro | ★★★★ | 2-4s | $1.25 / $10 |
| Qwen2.5-VL-72B | ★★★★ | 本地部署 | 开源 |

### 4.2 GUI 专用模型

| 模型 | 参数量 | 训练数据 | 适用场景 |
|------|-------|---------|---------|
| OmniParser v2 | ~1B | 截图 + 元素标注 | 截图解析为元素列表 |
| UI-TARS-7B | 7B | 200M+ GUI 操作 | 端到端 GUI 操作 |
| ShowUI-2B | 2B | 通用 GUI grounding | 轻量级坐标定位 |
| SeeClick | 9B | LLaVA + GUI 数据 | Web/Mobile/Desktop 通用 |

### 4.3 当前视觉识别的瓶颈

**1. 坐标精度天花板**：即使最强视觉模型，输出坐标也有 ±5-15 px 偏差，小按钮容易点错。

**2. 高分辨率代价**：4K 截图 → 视觉 token 爆炸（单图 5000+ tokens），成本和延迟暴涨。

**3. 滚动一致性差**：视觉模型无法理解"屏幕外还有内容"，需要外部辅助滚动逻辑。

**4. 动态内容混淆**：加载动画、骨架屏、loading 状态会让视觉模型产生幻觉。

**5. 中文 / 复杂字体识别**：当前主流模型对密集中文文本、艺术字体识别率低。

## 五、未来 1-3 年预判

### 5.1 短期（2026 下半年 - 2027）

**预判 1：混合路线（路线 C）成为事实标准**
- Browser-Use 模式被广泛采用，所有主流 Web/Mobile Agent 都会同时使用 Tree + 截图
- 纯视觉路线会退守到 Computer Use 等通用桌面场景

**预判 2：GUI 专用小模型快速普及**
- UI-TARS、OmniParser 这类专用模型会被集成进通用 Agent 框架
- "通用 LLM 决策 + 专用视觉模型执行 grounding" 成为典型架构

**预判 3：成本下降 10-50 倍**
- 视觉 token 价格大幅下降（参考 GPT-4V → GPT-4o-mini 的下降幅度）
- 本地视觉模型（7B 以下）能在消费级 GPU 上运行
- 让"每步都调 LLM"在生产环境变得经济可行

**预判 4：Accessibility Tree 标准化加速**
- 政府无障碍法规（GIGW、ADA、EAA）倒逼 App 开发者完善 AX 属性
- Flutter / RN 等跨平台框架增加更好的 AX Tree 输出
- 让结构化感知路线的覆盖率从 70% 提升到 90%+

---

### 5.2 中期（2027-2028）

**预判 5：原生 OS 级 Agent API 出现**
- Apple、Google、Microsoft 会推出 OS 级 AI Agent API
- 类比当前的 Accessibility API，但更适合 LLM 调用
- 取代部分 Appium / WebDriver 协议

**预判 6：Self-Healing 测试成为基础能力**
- 所有商业测试框架都会内置 LLM 自愈
- locator 失败 → 自动 LLM 重新定位 → 自动更新 locator 配置
- 测试维护成本降低 50%+

**预判 7：模型上下文窗口达到 10M+ tokens**
- 整个 App 的所有页面 Tree + 截图历史能全部放入上下文
- Agent 能"记住"整个 App 的导航结构，无需每步重新探索
- 多步任务成功率从 60% 提升到 90%+

**预判 8：视觉 + 触觉 + 音频多模态融合**
- Agent 开始理解音效、振动、TTS 反馈
- 不仅看屏幕，还能听到 App 的反馈（错误提示音、成功音）

---

### 5.3 长期（2028+）

**预判 9：UI 自动化范式转变**
- 从"测试工程师写脚本" → "测试工程师写需求，Agent 生成 + 执行 + 维护"
- 用例文件可能消失，被自然语言任务库取代

**预判 10：测试用例自动生成 + 自动维护闭环**
- Agent 通过探索式测试自动发现路径 → 生成用例 → 自我维护
- 类比 Fuzzing → Coverage-guided Fuzzing → AI Fuzzing 的演进

**预判 11：视觉识别精度逼近人类**
- 端到端 GUI 模型坐标精度达到 ±1-2 px
- 视觉感知不再是瓶颈，瓶颈转移到任务规划和推理

## 七、关键技术风险

### 7.1 短期风险

- **LLM API 成本不可控**：每步都调 LLM 在大规模回归测试中成本可能爆炸
  - **对策**：缓存 LLM 决策 + 用例分级（关键路径用 LLM，简单路径用确定性 locator）

- **LLM 决策不确定性**：同一用例两次执行结果可能不同，CI 报告难以信任
  - **对策**：固定随机种子 + 多次执行投票 + 阈值断言

### 7.2 中期风险

- **专用模型快速迭代**：今天集成的 OmniParser 半年后可能被新模型替代
  - **对策**：抽象层设计，保持视觉模型可替换

- **OS 厂商封闭 API**：Apple / Google 可能限制第三方 Agent 访问
  - **对策**：保持多协议支持（CDP / Appium / OS API）

### 7.3 长期风险

- **范式革命**：如果 OS 级 Agent 普及，整个 Appium / Playwright 生态可能边缘化
  - **对策**：RodSki 的关键字抽象层是护城河，可适配任何底层协议

## 八、总结

| 路线 | 当前推荐度 | 2027 推荐度 | 2028+ 推荐度 |
|------|-----------|------------|-------------|
| 路线 A 结构化 | ★★★★ | ★★★ | ★★ |
| 路线 B 纯视觉 | ★★ | ★★★ | ★★★★ |
| **路线 C 混合** | **★★★★★** | **★★★★★** | ★★★★ |
| 路线 D E2E 视觉 | ★★ | ★★★★ | ★★★★★ |

**当下最优选择**：**路线 C（混合感知）**，长期演进方向是 **路线 D（E2E 视觉模型）**。

**RodSki 的核心战略**应该是：
1. 短期：把混合感知（Tree + 截图 + LLM）做扎实，覆盖 Web 和 Mobile
2. 中期：把视觉层抽象出来，能灵活切换通用 LLM 和专用模型
3. 长期：保持架构开放性，准备迎接 OS 级 Agent API 和 E2E 视觉模型范式
